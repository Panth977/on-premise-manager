Agent GUI (routes)

Agent 0.14.1: one action — Commit (SPEC §21 #105)

There is no working copy and no draft any more. Every edit stays in your browser (kept in local storage, so a reload loses nothing) until you press Commit… and give a message — that writes the commit directly. The bar on every config page shows N changes (not committed) · Discard · Review · Commit…; drawers and dialogs Apply into it, there is no Save button. If someone else committed meanwhile, your changes are rebased onto the new head (automatically when nothing conflicts). On a site, a Commit in the agent GUI also applies the changes to the containers (a failed apply writes no commit); there, "uncommitted" means only changes made on the server outside the agent — commit those first. Details: branches-commits.md §15.

Agent 0.15.1: one Commit = one transaction, including the files (SPEC §21 #107)

Editing a file — a volume's starter content (create, edit, rename, move, delete, upload files or folders), a File's content, a volume archive — is a pending change like any other: nothing is uploaded while you edit and there is no Apply or Save content button. The bytes stay in your browser (memory + IndexedDB, so a reload restores them too) and the change bar counts every file; Review shows a per-file diff. Commit… first uploads only the new files to a staging area ("Uploading 2 of 5 files · 1.2 MB of 3 MB"), then writes the commit; the server checks every file, moves it into the store and only then makes the commit visible. If anything fails — an upload, validation, someone else committed first, the network — nothing is committed, the staged files are deleted and your changes (files included) stay in the browser so you can retry. Drafts: everything you have not committed is auto-saved in this browser (IndexedDB) per account; after a refresh or when you come back you are asked “You have unsaved changes from <time> (N changes) — Restore or Discard?”. A draft is only offered when it was made on the current latest commit — otherwise it is discarded with a notice. Drafts expire 1 hour after the site was last open in any tab (an open tab keeps them alive) and are deleted when you log out. Details: branches-commits.md §16.

Agent 0.14 / §21 #104: the Branch page

Deployment › Branch replaces Diff: the cloud head (commit, message, author, staged), this site's branch (ahead / behind), Uncommitted (your GUI edits plus changes made on the server by hand: containers, images, env, ports, files, persist-volume content) with Commit… / Discard, Merge from cloud (cherry-pick; deletions = "remove locally"; refused while anything is uncommitted), Fast-forward all sites and History (revert / reset). There is no local proposal and no approve countdown; Roll back to a snapshot keeps the 60 s wait and asks for a commit message. See branches-commits.md.

Every agent serves the same GUI in three ways (all three need the same login with the deployment access key, then the "Who is working right now?" popup): (1) https://<any edge host>/_opm/ through the agent edge (embedded Caddy, ports 80/443), (2) http://<site host>:8080/_opm/ (agentGuiAliasPort, from the agent itself, so it works when the edge cannot bind 80/443), (3) http://<site host>:7080/_opm/ (agentPort, also the mesh). Whichever site you open, you see all sites of the deployment. Below is a clickable wireframe of every route. The address bar shows the exact route.

The same forms as the cloud console (§21 #102)

The agent GUI renders the cloud console's forms from the shared package ui/: the container page, the edge host drawer, route page, nginx import and Test a URL, the volume drawer, site settings, the dev-tool preset / connection drawer, and the persist settings. What you can change locally

Allowed on the site (§21 #113: a site is standalone, like Portainer with commit history)

  • Variables, secrets and files: add, change the whole definition and the value / content, remove
  • Containers: add (pick an image: a catalog version, a docker reference pulled by this host, or an image already on the host), duplicate, remove, Change image…, and every field: env, mount sources, ports, restart, resources, depends, command
  • The site label and dev-tool presets
  • When Docker is changed outside OPM (docker run / compose): shown as uncommitted, or committed by the agent as UNKNOWN (changed in Docker) — the site's drift policy on the Branch page
  • Site volumes: add, edit label / description / Back up / location, remove an unused one (Config → Volumes). The kind (folder / single file) is fixed after create. Starter content and Persist to cloud are shown read-only: they change only in the cloud console (§21 #101, V_LOCAL_VOLUME_CONTENT).
  • agentPort, agentGuiAliasPort, not-found page (Config → Settings)
  • The edge: ports, body limit, hosts, TLS modes, response headers, routes (route page), and Import from nginx.conf… (Config → Edge; rules)
  • Reset a volume of THIS site to its starter content (Backups → volumes; 60 s + ACCEPT, a snapshot first; how). This is an action, not a proposal.
  • Site depends

Only from the cloud

  • Add or remove a site
  • A volume's Persist to cloud setting and its cloud content versions (§21 #101)

Every local change is one commit of the site's branch, applied through the same engine as a cloud merge (a pre-update snapshot first), so History → Revert / Reset rolls it back. Merge it into the cloud from the deployment's Agent branches page.

The 60-second wait and ⏩ Hold to fast-forward

Approve, Roll back, Reset to starter content, Empty and Restore all show the same countdown. Next to Cancel is ⏩ Hold to fast-forward: hold it (mouse, finger, or Space / Enter on the focused button) and the wait runs twice as fast at once, four times as fast after 1.5 s. Let go and it slides back to normal speed. The agent counts the wait itself, so the shortest possible wait is a quarter (15 s of 60); if the browser stops sending "still holding" for 1.5 s, the agent goes back to normal speed by itself. A fast-forwarded approval shows "fast-forwarded (×4, 18 s real)" in the Diff history and in the activity.

A database that keeps restarting after an image upgrade

When a container keeps restarting and its log says DATA DIRECTORY / IMAGE VERSION MISMATCH (custom-pg) or database files are incompatible with server (PostgreSQL), the Status page shows a hint with Copy data volume aside, then empty it: the volume is copied to volume-copies/ with the container stopped, then emptied (60 s + its name), and the container starts with a new, empty data directory. The old data stays in the copy (Docker → Volumes → Copies) to restore or migrate later.

Image names in the GUI

The Status and Config pages show each container image as <serviceSlug>:<version>, for example northwind-backend:v1. This is the same name that docker ps shows on the server. The source reference of the image (the docker tag in the registry) stays in the cloud. Volume mount paths can use {{ container.env.NAME }}: the GUI shows the resolved path. The container view's volume rows use the same single grouped dropdown as the cloud (Data volumes with "shared with X" and "+ New data volume…", Files, Secrets, Advanced: host path…, Not mounted); Read-only is a toggle only for volume / host (off = read-write). The column "Inside the container" shows file / secret rows as text "mounted read-only at <path>" with an Edit path link, and "shared copy · also used by X" when other containers mount the same file / secret. The Files page shows "On the server" for every file (one copy per site at its location; agent home = the agent data dir) and "Preview for site…" for files with expressions; the Volumes section shows the location and the absolute folder. See Image names on a site.

Docker section and the container page (operator toolbox)

The Docker section of the sidebar holds Containers, Volumes, Docker and Network for the selected site. Click a container to open its own page (/_opm/app/<site>/containers/<container>) with the tabs Overview (state, health history, ports, mounts, environment with secret values masked, restarts, image, depends and start order), Logs, Terminal, Monitoring, Inspect, Processes & events and Config (the container editor; edits become a local proposal). The Status page rows have quick actions that open these tabs. With * (All sites), Containers, Volumes and Docker show every reachable site. Turning tools off

A client can switch off the shells in /etc/opm/agent.json: "tools": {"hostShell": false, "containerExec": false} (both on by default). "devTools": false in the same object switches off Dev tools (agent 0.11.0). The GUI then hides them and says how to turn them on. "hostShell": {"user": "opm"} runs the host shell as another user (the agent must run as root for that).

Transcripts

Terminal transcripts record what the terminal SHOWED (not your keystrokes). They stay on the site for 7 days and are never uploaded to the cloud. Every secret value the site knows is replaced by •••••• before anything is written; a secret the agent does not know (for example a password the application prints) is not masked, so treat transcripts as sensitive.

Transfers (Send + Receive in one module, agent 0.11.2)

Agent › Transfers (/_opm/app/{site}/transfers, one site; under "All sites" it asks for a site) shows two columns: Send (this site → cloud) on the left and Receive (cloud → this site) on the right; at phone width Send comes first. The old …/send and …/receive URLs redirect here.

  • Send is one button with two choices: Browser (pick a file on this computer; it is stored on the site first) or Path (a picker of the server's whole filesystem from /: folders load when opened or expanded, breadcrumbs, a typed path box, up, a hidden-files switch, size and modified time). Only files can be sent (tar a folder on the server first); files over 2 GiB, folders the agent cannot read ("no permission") and blocked paths (the agent's own data, /proc, /sys, /dev, /run, password databases, SSH host keys) cannot be picked. Listing is read-only and not logged; sending writes transfer.sent.
  • Store-and-forward: a sent file is queued on the site, uploading (with %) while a direct or relay route to the cloud exists, then stored in the cloud — whether or not anyone has the cloud page open. Retries show their count and last error. A file from the cloud is pending until the agent is online, downloading, then on this site; Save on server and Download are available once it is on the site.

Presets and manual connections

Presets (from the cloud)

  • Defined on the site's Dev tools tab in the cloud template or deployment (how) and stored as SiteConfig.devTools; they reach the site with the revision.
  • Id p:<presetSlug>. Read-only on the agent: Edit and Delete are refused; Duplicate to edit locally makes a manual copy (expressions kept).
  • Credentials are never literals: {{ secret.x }} / {{ var.y }} / {{ containers.<c>.env.<NAME> }} (agent 0.11.1, §21 #99: the final env value of that container, e.g. its POSTGRES_PASSWORD) expressions resolved on the site at use.
  • A local proposal cannot change presets (they are cloud configuration).

Manual (on the site)

  • Always available: Add connection → kind → target (a container + port of this site, host : port, an http(s) URL, or for SQLite a file in a declared site volume or a path inside a container) → authentication → options. Test works on the unsaved form.
  • Id c_<ULID>, stored in the agent database of that site and shared by every operator of the site.
  • A password / token is None, a secret expression, or a stored literal. Expression fields complete containers.<c>.env.<NAME> too (names from the head; values stay on the agent, secrets masked in the preview).
  • Not deployment state: not in snapshots, .opmsnap or .opmlog; a rollback does not touch them.

Remembered connections. The agent keeps one pooled client per connection: it connects on first use and reuses the client for the next query, closes it after 10 min idle (devTools.idleTimeoutSec), on Disconnect, when the connection (or its preset, or a rotated secret) changes, and reconnects once by itself when a query fails on a dropped connection. A container target is reached on its site-network IP, or through its published port on 127.0.0.1 when that IP is not reachable (Docker Desktop / Colima); the frame shows which.

Credential modes (§21 #103): None · Value (typed, masked, show / hide toggle; a manual connection keeps it on the agent) · Secret · Container env · Expression — the same control as the cloud preset drawer. A preset whose password / token is a static Value from the cloud config is shown masked in the read-only preset form; its View is below the form, and Duplicate to edit locally copies the value.

Credential reveal. A stored literal is shown as •••••• in every read. View shows it for 60 s (the same RevealValue countdown as secrets, at most 30 per minute), and writes devtools.credential-revealed. Change replaces it; saving with the masked value keeps the stored one. Expressions are not revealed here (reveal the secret itself). The same applies to secret variables of HTTP environments.

SQL workbench (PostgreSQL, SQLite, Cassandra)

  • Editor (CodeMirror, loaded only on dev tools pages): dialect highlight, schema completion (namespaces, tables, columns with type and 🔑, functions), hover cards, lint of unknown tables / columns, find / replace, multi-cursor, folding. Mod-Enter runs the selection, else the statement under the cursor; Shift-Mod-Enter runs all; Mod-S saves; Mod-/ comments. An error position is marked in the editor.
  • Tabs per site + connection, remembered in the browser (text, params — never credentials). Params panel for $n / ?, transaction toggle (PostgreSQL / SQLite; rolled back on error), timeout and rows per page per run, Cancel for a running query.
  • Schema tree: schemas / keyspaces → tables, views, materialised views (row estimate, size) → columns; functions; a table drawer with indexes, constraints and the DDL. A DDL statement refreshes it.
  • Results: one pill per statement (errors red: code, position, detail, hint; the rest is skipped after an error), command tag, rows affected, notices. Virtualised grid: 1000 rows per page with Load more (10 000 buffered for 15 min), filter + sort on loaded rows, column resize, cell / range / row selection, copy as TSV, sum / avg in the status bar, export CSV / JSON / NDJSON, value viewer (Text / JSON / Hex, date formats) with Download full value for cells over 64 KiB.
  • Inline edit for SELECT * FROM table results whose primary key columns are all present: edit cells, set NULL, delete rows, add rows; Save… shows the generated DELETE / UPDATE / INSERT and runs them in one transaction (logged and classified like any statement). Not for Cassandra, read-only connections or truncated cells.
  • Explain: PostgreSQL plan tree (self time bars, estimate vs actual warning, filters) + text; Analyze = EXPLAIN ANALYZE. SQLite shows EXPLAIN QUERY PLAN; Cassandra has none.
  • Saved queries per site (folders = collections, shared by operators, unredacted — the operator's explicit store).

Destructive statements, read-only connections, logging

  • Typed confirm. A destructive statement (DROP / TRUNCATE, DELETE / UPDATE without WHERE, ALTER …, FLUSHALL / FLUSHDB / CONFIG SET / DEL with a pattern-like key, clearing a retained MQTT message) opens a confirm with the reasons and the statement: type the connection name to run it. The agent re-classifies on the server; the GUI warning is advice.
  • Read-only connections are enforced by the agent: PostgreSQL in a READ ONLY transaction (transaction control refused), SQLite opened read-only, Cassandra and Redis write commands refused, MQTT no publish, HTTP only GET / HEAD / OPTIONS.
  • Every execution is logged as devtools.query with the actor, connection, target, the statement / command / request redacted (passwords, tokens and every secret value of the site → ••••••, at most 4 KiB), duration, rows, status — never result data. Forwarded actions are logged on both sites. Schema browsing and the Redis key browser are not logged (reads of metadata).
  • Limits: 30 s default timeout (up to 3600 s), 8 running executions per site, 120 executions per minute per session.
Turning Dev tools off

/etc/opm/agent.json "tools": {"devTools": false} (default true) switches Dev tools off on that site: every dev tools page shows "Dev tools are turned off on this site" with the reason and a link to the setting, and the API answers 403. The switch is also on Agent → agent.json → Edit settings (Dev tools; saving restarts the agent). Limits live in "devTools": {…} of the same file (edit the file + restart). Agents older than 0.11.0 have no Dev tools and do not show the switch.

Hard fallback

If the upgrade from this page or from the cloud cannot run (or you need a downgrade or a clean reinstall), rerun the site's install command on the server. It asks "Installed A → available B: UPGRADE | DOWNGRADE | SAME", keeps agent.json, the site key, the data and the enrollment, backs up the database, and rolls back by itself when the new agent is not healthy within 60 s. Without a terminal add OPM_YES=1 after sudo. Details.

An agent older than 0.10.0

An older agent (for example 0.7.2, where sudo opm-agent upgrade says "unknown command") has no Agent page. Upgrade it once by running the site's Upgrade / reinstall command on the server (cloud Setup page → the site's card → View → Copy; always viewable, or Regenerate for an upgrade-only command). After that, upgrades are a button here or in the cloud console.
