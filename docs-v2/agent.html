On-prem agent

The agent (internals)

The agent is one Go binary for each site. It runs as the systemd service opm-agent as root, because it uses the Docker socket. It keeps its data in SQLite, and has an edge: Caddy v2 embedded as a Go library (in process, not a child process or a container) that owns host ports 80/443 and routes user traffic to the containers. The agent GUI is on the edge at /_opm/, on agentGuiAliasPort (default 8080) and on agentPort (default 7080, also the mesh). It talks only to the cloud API and to the other sites of the same deployment.

Rules

  • Only the agent writes in /var/lib/opm.
  • The site key never leaves the server.
  • Secret values are stored in SQLite like variables (plain, prototype). The GUI shows ••• and View reveals a value for 60 s (any number of times) with an audit activity. The agent writes ONE copy per site of each mounted secret to a tmpfs directory with mode 0400; every container that mounts it shares that file.
  • The agent never prunes an image layer that a kept snapshot uses.
  • Before every snapshot the agent checks that the free space is at least 1.2 × the estimate.

SQLite tables

One file, /var/lib/opm/opm.db, in WAL mode. Times are Unix seconds (INTEGER) unless the column says TEXT ts (ISO 8601). JSON columns hold canonical JSON (RFC 8785).

Container driver

What the driver does

  • It talks to the Docker Engine API on /var/run/docker.sock. The config names the runtime; Docker is the first driver.
  • It makes one bridge network per site: opm_<deploymentId>_<siteSlug>. Each container joins it with the DNS name = its containerSlug (the container name; one image can run as several containers).
  • It names a container by its containerSlug, exactly as the site config declares it: docker ps shows mqtt, backend. With "containerNames": "prefixed" in agent.json the name is opm_<deploymentId>_<siteSlug>_<containerSlug> instead (use it when several sites share one Docker host). The labels are opm.container (containerSlug) and opm.service (serviceSlug).
  • Each container has two DNS names on the site network: the containerSlug and, for older references, opm_<deploymentId>_<siteSlug>_<containerSlug>. In expressions use {{ containers.mqtt.host }} and {{ containers.mqtt.port.mqtt }} (see Expressions).
  • It finds its containers by their labels, never by name. When the naming mode changes (or after an upgrade from the prefixed names), the agent renames its containers in place at start and before each update. A rename does not recreate a container: the name is not part of the spec hash.
  • If the name is already used by a container that this site does not manage (for example one made with docker run --name mqtt, or a container of another site), staging fails: "Docker container name mqtt is already used by a container not managed by this site (id …, image …) — remove or rename it, or set containerNames: prefixed". The agent never touches that container.
  • It runs each container from the readable image reference <serviceSlug>:<version> (for example northwind-backend:v1). See Image names on a site.
  • It sets these labels on every container: opm.deployment, opm.site, opm.service, opm.rev, opm.spec_hash.
  • It does not touch containers without the opm.deployment label. It shows them on the status page as "not managed".

The recreate rule

The driver builds a container spec for each container from the config: image digest, env (resolved), mounts (mount paths resolved after env), port bindings, command, restart policy, resources.

spec_hash = sha256 of the canonical JSON of that spec.

  • Same hash as the running container → do nothing.
  • Different hash → stop, remove, create, start.
  • Container is in the config but not running → create, start.
  • Container runs but is not in the config → stop, remove. Its volume folders stay on disk.

Image names on a site

The agent gives each loaded image two names. Both point to the same image.

Edge (embedded Caddy)

The edge routes user traffic. It is Caddy v2, linked into the agent binary as a Go library (github.com/caddyserver/caddy/v2). It is not a child process and not a container, so the agent controls its full life cycle.

SiteConfig.edge → Caddy JSON → caddy.Load (graceful) → listeners on 80/443 → containers on the site network.

How it works

  1. The agent builds Caddy JSON from SiteConfig.edge (after expressions resolve): one HTTP server per edge port, one host matcher per edge.hosts[] entry. Per host, the OPM handler opm_route chooses the route like nginx (exact, longest prefix, stop regex, regex, internal rewrites) with the same Go code as Test a URL. Then the chosen route runs: response headers, WebSocket guard, body limit (413), readiness (503), the upstream path (strip / rewrite / add prefix) and a reverse_proxy to the container's loopback port over HTTP/1.1, or the opm_redirect handler. The transport opm_http gives nginx-like idle timeouts: a stream that keeps sending (SSE, a download, a WebSocket) is never cut. Details: Edge routing.
  2. It always adds, first on every host: /_opm/* → the agent GUI handler (in process). Last on every host: the not-found page (404). The edge's own pages: 404 (not-found page), 413 (body too large), 500 (rewrite loop), 503 (not ready / upstream error); response headers marked always are added to them. A proxy upstream that fails its health check → the not-found page with 503.
  3. caddy.Load(json): Caddy swaps the config gracefully on sockets the agent owns (it binds each edge port once and passes Caddy a copy, fd/<n>). Open connections finish (30 s grace); the listening socket is never closed during an update.
  4. The edge always runs: before the first update it is the built-in default edge on port 80 (GUI on /_opm/, / → /_opm/app, other paths → "No configuration applied yet").
  5. TLS: Caddy CertMagic, storage /var/lib/opm/certs/. Modes: none, internal (Caddy local CA), acme (Let's Encrypt; http-01, tls-alpn-01, dns-01), files (cert from a deployment file, key from a secret).
  6. Docker containers reach nothing on 80/443: the agent rejects a container hostPort of 80, 443 or an edge port.

Failure rules

  • Reload fails (invalid JSON, port in use, bad certificate file): Caddy keeps the previous config running. The agent writes edge.reload-failed and fails the APPLY step → automatic rollback of the update on all sites.
  • Reload succeeds: activity edge.reloaded { revSeq, hosts, routes }.
  • Port 80/443 cannot be bound (another program, no permission): alert edge-port-bind-failed, activity agent.port-bind-failed (once, with the owner process when Linux tells). The agent retries every 30 s. The GUI stays reachable on agentGuiAliasPort and agentPort.
  • Certificates: cert.issued, cert.renewed, cert.failed (an alert). ACME renews 30 days before expiry; internal certificates live 12 h and renew themselves.
  • Peer traffic never goes through the edge, so a broken edge never breaks the mesh.

Browser internet tunnel

A site can have no internet and no peer with internet. Then a person can open /_opm/app/internet in a browser that HAS internet and click Start. The tab becomes the internet source of that agent. Only ONE tab can do this for each site. To use a new tab, first revoke the old tab (or stop it there).

Route order for each cloud call

  1. Own internet (api.opm.example:443).
  2. A peer with internet (/_opm/peer/relay).
  3. The browser tunnel (only while a lease is active).

See Networking → tunnel for the security note.

Tab loop

  1. GET /_opm/api/tunnel/next (waits ≤ 25 s, returns ≤ 4 requests).
  2. For each request: fetch(url) to the cloud. The request is sealed: the tab sees POST /v1/agent/sealed and ciphertext.
  3. POST /_opm/api/tunnel/result { reqId, status, headers, body }: ciphertext again, only the agent can open it.
  4. No poll for 30 s → the lease expires.

Peer mesh

How sites talk

  • Each agent calls the others at http://<site.host>:<agentPort>/_opm/peer/*.
  • Every request is signed with the site key (Ed25519). Headers: X-OPM-Site, X-OPM-Ts, X-OPM-Nonce, X-OPM-Sig over METHOD\nPATH\nTS\nNONCE\nsha256(body).
  • The receiver rejects a request if |now − ts| > 60 s or it saw the nonce in the last 5 min.
  • Each agent pings every peer every 10 s. A peer is reachable if it answered in the last 30 s.
  • The GUI of any site shows all sites: the agent fetches peer data over the mesh. A site that does not answer shows "stale · last seen hh:mm".

Smart distribution

Every agent with internet talks to the cloud on its own: its own poll, its own downloads, its own reports. When some sites have no internet, the sites share what they have over the mesh.

Cloud view: latest fetch wins. Blobs: peer first, then one fetcher per blob, then copy over the local network.

Cloud view (every 10 s)

  • Each agent keeps cloudView = { fetchedAt, cursor, proposals[], transfersToSite[], draftHead }. fetchedAt is the cloud server time of the poll answer.
  • The agents exchange it with GET /_opm/peer/cloud-view.
  • An agent takes a peer's view only if its fetchedAt is newer. Equal time: keep the own view.

Blobs (image layers, files)

  1. Ask the peers (GET /_opm/peer/have). A peer has it: copy over the local network.
  2. No peer has it, and this site has internet and is the fetcher: download from the cloud.
  3. Else ask the fetcher (POST /_opm/peer/fetch-request), wait, then copy from it.
  4. Check the sha256 of every copy. A bad copy is deleted and fetched again.
One fetcher per blob

The fetcher is the internet site with the highest sha256(blob sha256 + siteSlug) (rendezvous hashing). All sites compute the same answer, so nothing is downloaded twice. If the fetcher goes away, the next site in that order takes over.

Relay for a site without internet

The site db has no internet. Its reports (heartbeat, activities, staging status) go through an internet peer, unchanged. It signs its cloud request and sends it to app at /_opm/peer/relay. app calls POST /v1/agent/relay. The cloud checks the signature of db, not of app.

Operator toolbox (agent/internal/tools)

The GUI's Tools pages call /_opm/api/sites/{site}/tools/* (contract shared/src/agent-tools.ts, SPEC §7.4, §21 #89).

  • Logs: Server-Sent Events from the Docker logs API (follow ≤ 6 h); the agent log tails the debug log files; the edge access log is a Caddy middleware (opm_access_log) that writes logs/edge-access.log (20 MiB × 5 files).
  • Terminal: a WebSocket per terminal, opened with a single-use ticket (60 s) from an actor-authorised request and refused for another origin. Container = docker exec with a TTY; host = a PTY running the login shell as hostShell.user. Output transcripts (asciicast) in transcripts/, 7 days, secrets masked, never uploaded.
  • Monitoring: every 15 s one-shot docker stats + inspect per container and /proc for the host, stored in metrics.db (raw 1 h, 1-minute 24 h, 15-minute 7 days, ≤ 64 MiB).
  • Containers: restart / stop / start (409 while an update runs); a manual stop is remembered in tools/manual-stops.json until a start or a new head.
  • Volumes (read only), network checks (host: native; container: the image's own tools) and Docker images / prune (never the head revision's images).
  • Other sites: JSON forwarded as usual, SSE copied with flushes, the WebSocket bridged with a signed upgrade; both sites log the terminal.
  • Limits: 4 terminals per site, 30 min idle, per-minute rate limits (terminal 10, actions 20, netcheck 30, downloads 20, prune 2).

Security model

  • No shell escape. The agent never runs a process for a dev tool. SQLite ATTACH / VACUUM INTO need a quoted path inside the same volume (URI names refused; rewritten to the absolute path). pg COPY … PROGRAM, COPY … TO|FROM '<file>', lo_import / lo_export / pg_read_file run on the database server as the DB user (the operator's database, not the agent host) and are flagged destructive.
  • HTTP client: refuses /_opm/api/* and /_opm/peer/* on any host (also after a redirect), drops any Cookie named opm_session*, never forwards the browser's cookies or headers, drops the Cookie header on redirects, never uses an environment proxy.
  • Auth: reads = session; executions, writes, reveals, MQTT sessions = session + actor (the Actor header is also the CSRF guard; the cookie is SameSite=Strict). The MQTT stream needs a single-use 60 s ticket bound to the GUI session.
  • Reveal: stored literals and secret environment values only (RevealValue 60 s, Cache-Control: no-store, 30 / min per session, devtools.credential-revealed).

Logging and redaction

  • Every execution writes devtools.query: actor, connection, kind, resolved target, op, the statement / command / request after redactStatement / redactHttpRequest, then every secret value of the site (≥ 4 chars) and the connection's resolved credentials → ••••••, cut to 4 KiB; duration, rows, status, readOnly / destructive / confirmed. Never result data. The client queryId is masked too.
  • Forwarded requests are logged on both sites: the executing site writes the action, the forwarding site writes devtools.action-forwarded { siteSlug, forwardedTo, method, action, connectionId, status }.
  • Not logged: schema introspection, the Redis key browser, refusals before execution (403 read-only, 422 confirm / blocked / invalid). Connection failures are logged (ok: false).
  • History = the devtools.query + MQTT publish activities of the site (last 30 days, cursor = activity seq).

Install and enroll

  1. Create the commandIn the cloud Setup page, an operator creates an install command for one siteSlug. The token is 32 random bytes, single use, and expires in 24 h. The cloud stores it (and its sha256) while it is active, so the command can be viewed again on Setup; after use, revoke or expiry it is cleared.
  2. Run it on the servercurl -fsSL -H "Authorization: Bearer <token>" https://api.opm.example/v1/install/script | sudo sh One copy-paste. To never let the script install Docker, put the switch after sudo: … | sudo OPM_SKIP_DOCKER_INSTALL=1 sh.
  3. Check the serverThe script prints numbered steps and logs everything to /var/log/opm-install.log. Preflight reports OK / MISSING for root, Linux, systemd, amd64 / arm64, curl, tar, kernel ≥ 3.10, cgroups, 2 GiB free in /var/lib and iptables / nftables (for a missing tool it prints the exact package command; it never installs distro packages).
  4. DockerA running Docker the agent can talk to (it negotiates Engine API 1.41–1.47: Docker 20.10 or newer, any install method) is used as is. A stopped one is started. A too old or too new one is not touched: the script stops and says what to do. No Docker: the script asks "Docker Engine is not installed. Install the pinned Docker 28.5.2 now? [y/N]". No → manual instructions (any Docker ≥ 20.10, then rerun), exit 1. Yes (or OPM_INSTALL_DOCKER=1 / OPM_YES=1 without a terminal) → it installs the pinned official static bundle (Docker 28.5.2, sha256 checked, from /v1/install/deps/docker) with systemd units and /etc/docker/daemon.json, and records it in /etc/opm/installed-deps.json.
  5. Check the binaryThe script downloads the agent of the pinned version (embedded when the cloud made the script, never "latest"; or ?version=x on the script URL / OPM_AGENT_VERSION=x for another uploaded version). It checks the sha256 and the Ed25519 release signature (openssl, else the installed agent's verify-release) before the new binary runs. When an agent is already installed it first asks: "Installed A → available B: UPGRADE | DOWNGRADE | SAME (reinstall) [y/N]" (see the hard fallback).
  6. Write the filesThe script writes /etc/opm/agent.json (with the release public key; an existing one is kept and only gains missing keys), the token file (never for an enrolled site) and the systemd units (written by the agent binary itself: opm-agent systemd-units --install = service + opm-agent.socket + boot guard), starts the agent, and waits until /_opm/api/health is ok (a fresh install: until the site is enrolled). When a step fails it shows the step, the last 20 log lines and a manual instruction; rerun the same command after fixing it. A rerun skips what is done.
  7. GUI addresses and firewallStep 7 lists the ports that really listen and prints the GUI URLs, port 80 first: http://<ip>/_opm/, then :8080 and :7080. It reports the host firewall (ufw / firewalld) with the exact commands to open 80 / 443 / 7080 / 8080 (it never changes rules), and curls each URL from the server (3 s timeout): "reachable / NOT reachable from this host". A cloud firewall (for example a DigitalOcean Cloud Firewall) cannot be seen from inside the server; open the ports there too.
  8. Boot guardPart of the units (an agent without systemd-units: opm-agent upgrade-guard --install): it writes /usr/local/lib/opm/upgrade-guard.sh and the drop-in opm-agent.service.d/upgrade-guard.conf (see systemd unit and Self-upgrade and rollback). An older binary without that subcommand is skipped with a note.
  9. Upgrade laterFrom agent 0.10.0 an upgrade is a button: cloud console → Setup → Upgrade agent (or Upgrade all), or the agent GUI → Agent page → Upgrade to X. Nobody needs to log in to the server. An agent below 0.10.0 (for example 0.7.2, where sudo opm-agent upgrade says "unknown command") upgrades once by rerunning its original install command on the server: after the site enrolled, that token only upgrades that site (no expiry; Revoke ends it), installs the pinned agent, writes the boot guard and restarts it, and never re-enrolls. After that, upgrades are a button.
  10. EnrollThe agent makes the site key and calls POST /v1/agent/enroll with the token and the public key. The cloud marks the token used and returns the peers. A site that is already enrolled gets conflict (revoke it first in the cloud).
  11. Wait for a personThe site config is empty. Nothing runs until a person opens the agent GUI, answers "Who is working right now?", and approves the first proposal.

Rerun the install command: the hard fallback

If the upgrade from the GUI or the cloud cannot run, or you need a downgrade or a clean reinstall, rerun the site's install command on the server (SPEC §19.1, §21 #91). It is safe: it asks before it changes anything, keeps the whole setup, and puts the old agent back by itself when the new one is not healthy. App containers keep running the whole time, except when you move the agent home on an upgrade to ≥ 0.19.1 (explicit OPM_MOVE_HOME or a yes at the terminal, never DRY_RUN): this site's containers stop for the move and start again.

Socket activation. /etc/systemd/system/opm-agent.socket holds the default edge port (80), agentPort (7080) and guiAliasPort (8080) in ONE unit with FileDescriptorName=opm and Service=opm-agent.service; the agent matches the inherited sockets by port and binds every other port itself. While the agent restarts (upgrade, restart, rerun of the install command) the kernel queues new connections instead of refusing them: measured 0 of 2184 requests failed with the socket, 4 of 2144 refused without it. Needs systemd ≥ 235; OPM_SOCKET_ACTIVATION=0 turns it off. All units come from the agent binary: opm-agent systemd-units --install.

Self-upgrade and rollback

Everything opm-agent can do on the command line is also in the GUIs (SPEC §7.5, §21 #90), including the upgrade. One code path serves the agent GUI (Agent page), a cloud request (Setup → Upgrade agent, picked up from the cloud view), the mesh Upgrade all and sudo opm-agent upgrade. It is never automatic. Requirements: agent ≥ 0.10.0, enrolled, no update / rollback / snapshot / restore running (else locked), no other upgrade (conflict), the version you saw is still the pinned one (stale), and the typed site slug.

Five phases, each written to upgrade/state.json and sent to the cloud at once in a heartbeat. A failure before the swap leaves the old agent running. After the restart, two independent layers put opm-agent.prev back when the new agent is not healthy within 60 s.
  1. DownloadSigned GET /v1/agent/release + GET /v1/agent/binary (direct or through the relay, resumable) into opm-agent.new; the GUI shows bytes / total.
  2. VerifyThe Ed25519 release signature (key from agent.json releasePublicKey, else the cloud's), the sha256, and a self-test: opm-agent.new version must print the pinned version.
  3. SwapThe running binary is hard-linked to opm-agent.prev; opm-agent.new is renamed over opm-agent (atomic). The boot guard is (re)installed and upgrade/pending.json written with a deadline.
  4. RestartThe old agent starts the watcher, then systemctl restart --no-block opm-agent (without systemd: graceful stop + re-exec). The containers keep running.
  5. HealthThe new agent finishes its startup (store, listeners, /_opm/healthz), writes upgrade/healthy, sets the phase done and writes agent.upgraded. Health = the public GET /_opm/api/health (200 ok / 503 not yet: store, listeners, startup, version, schema, cloud, Docker, socket activation). GUI sessions survive: the page polls /_opm/api/health every 2 s and continues on the same login.

Layer 1 · the watcher

The known-good binary runs as opm-agent.prev upgrade-watch outside the service (systemd-run --unit opm-agent-upgrade-watch-<id> --collect, else a detached process). It waits for upgrade/healthy and the new version on /_opm/api/health. At the deadline without them: stop the agent, rename opm-agent.prev back, start it, write upgrade/rolled-back.json.

Layer 2 · the boot guard

upgrade-guard.sh runs before every (re)start of the service (ExecStartPre=-). When pending.json is past its deadline without healthy and the binary still has the new sha256, it restores .prev. This covers a new binary that crash-loops and a reboot during the watch. A broken binary cannot guard itself; a systemd watchdog would need support in every old version.

The restored old agent reads rolled-back.json and writes agent.upgrade-failed + agent.rolled-back (actor = the person who asked). Activities: agent.upgrade-started (old agent), agent.upgraded (new agent), agent.upgrade-failed, agent.rolled-back.

  • From the cloud: Setup queues a request (agents/{site}.upgradeRequest, 24 h). Each agent takes only its own, once per request id (remembered in upgrade/handled-requests.json), with the requester's email as the actor. The heartbeat reports every phase; the cloud clears the request when it is done, failed or rolled back. If the pin moved meanwhile the agent fails it with "the pinned release moved to X; request again".
  • Upgrade all: one site at a time, in site order, stop on the first failure. In the agent GUI the site you opened coordinates and upgrades itself LAST (it restarts); state in upgrade/run.json. In the cloud the run lives on the deployment; the next site is queued when the previous one reports done.
  • The third layer is you: when nothing else works, rerun the install command.
  • Agents below 0.10.0 have none of this: rerun the original install command on that server once. It installs the new agent and the boot guard; after that, upgrades are a button.
