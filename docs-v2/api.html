The cloud backend has one HTTP API at https://api.opm.example/v1/…. The cloud frontend and every agent use only this API. All bodies are JSON unless the endpoint says multipart or raw.

One identifier per entity in every path

Each entity has one id, and the path uses that id: {registryId}, {serviceSlug}, {version} (an image inside its service), {iconId}, {notFoundPageId}, {templateId}, {tagSlug}, {uid}, {deploymentId}, {siteSlug}. A service has no other id: /v1/services/northwind-backend/images/v1. The image version (for example v1) is the OPM version. It is not the docker tag. The docker tag is part of the image reference (for example docker.io/northwind/backend:3.0.9).

One API, two kinds of callers

Firestore and Storage security rules deny all client access. Only the API (server side, Admin SDK) reads and writes data. This keeps a later move away from Firebase simple.

Auth for people

  1. Log inThe frontend logs in with the Firebase Auth client SDK (email + password, or Google SSO for the org domain). There is no signup.
  2. Send the tokenEvery request has Authorization: Bearer <Firebase ID token>. The SDK refreshes the token every hour.
  3. Server checkThe API verifies the token, loads accounts/{uid}, refuses a disabled account (forbidden), and evaluates the access rules for the resource and action of the endpoint.

Auth for agents: signed requests

An agent has an Ed25519 site key (made at install). It signs every request. The cloud has the public key from enroll. Agents use the same headers to talk to each other over the mesh.

HeaderValue
X-OPM-Site<deploymentId>/<siteSlug>
X-OPM-TsUnix time in seconds
X-OPM-Nonce16 random bytes, base64url
X-OPM-SigEd25519 signature (base64url) of the string to sign
  1. Hash the bodyCompute sha256(body) as lowercase hex. Use the empty string for a request without a body.
  2. Build the string to signMETHOD + "\n" + PATH + "\n" + TS + "\n" + NONCE + "\n" + bodyHash. PATH includes the query string exactly as sent.
  3. SignSign the UTF-8 bytes with the site private key. Put the result in X-OPM-Sig.
  4. Server checkRefuse if |now − TS| > 60 s, if the nonce was seen in the last 5 minutes, if the site is not enrolled, or if the signature does not verify. Error code: unauthenticated.

Install token: only /v1/install/* and /v1/agent/enroll accept Authorization: Bearer opi_…. The token is single use and valid for 24 hours.


Agent GUI calls: login session + declared actor


Two layers. (1) POST /_opm/api/login { accessKey } checks the deployment access key against accessKeyHash and sets the cookie opm_session (HttpOnly, SameSite=Strict, Secure on https). The session ends 6 h after login; there is no sliding renewal. After that every /_opm/api/* call answers 401 with code session-expired and the GUI goes to /_opm/login. (2) After login, on every page load the popup "Who is working right now?" calls POST /_opm/api/actor { email } → an actor token (page memory, expires with the session). Every write sends the cookie AND Authorization: Actor <actorToken>; the agent writes the email + sessionId into the activity. Missing cookie → 401 unauthenticated; missing actor token on a write → 401 actor-required.



CORS for the browser tunnel
The browser tunnel (networking) makes agent calls from a browser tab, sealed end to end (/v1/agent/tunnel-key, /v1/agent/sealed). So the cloud answers CORS on /v1/agent/* (any origin, methods GET / POST / PUT / PATCH / DELETE, headers X-OPM-* and Content-Type, no cookies) and the Storage bucket allows GET / PUT from any origin for signed URLs. The agent signature is the authorization, not the origin.

The edge uses the round E shape (rules). A client that still sends the older shape (match.pathPrefix, proxy timeoutSec, no response headers or body limits) is normalized on write, not refused: pathPrefix → a prefix route, timeoutSec → readTimeoutSec, websocket kept. Audit log: every root write is logged


Every request from a person that is not a GET and is not inside one deployment (/v1/deployments/{deploymentId}/…) writes one entry in the root audit log, whether it worked or not. This covers registries, services, images, icons, 404 pages, templates, tags, accounts, uploads, blobs, and creating, changing or deleting a deployment. A refused request (403, 404, 409, 422, 500) is logged with its status and error code. Changes inside a deployment (drafts, publish, secrets, setup, transfers) go to that deployment's activities instead — except the credential calls (View / Regenerate of the access key, install command and secrets), which write BOTH the activity and a root audit entry (deployment.access-key-revealed, deployment.access-key-rotated, deployment.install-command-created, deployment.install-command-revealed, deployment.secret-revealed, deployment.secret-regenerated).


    

  • Each entry has the endpoint name (op), the person (uid and e-mail), the action (for example template.updated), the outcome, the HTTP status, the target document (for example templates/{id}), the request id, the IP address and the user agent.
    • 

  • changes is a before → after diff of the target document, one row per changed field (for example variables[port].value: 8080 → 9090). A create stores the new document; a delete stores the deleted one. There are at most 200 rows, and a value larger than 2 KB is cut to a preview.
    • 

  • Secret values are never stored in an audit entry. A registry password, a secret value in a template or deployment, or any key that looks like a password, token or private key is shown as ***. A changed secret is marked "secret changed". Passwords, reset links, access keys and install commands are never in an entry, also not inside a stored object (lastSetPassword.value → ***).
    • 

  • Every credential can be viewed again and regenerated any time. Account credentials are audited as account.password-set, account.password-revealed, account.reset-link-created and account.reset-link-revealed; registry passwords as registry.password-revealed.
    • 

  • Two cases are not logged: a request without a valid login (401), and each part of a multi-part upload. The upload is logged when it is created and when it completes, with the part count.
    • 

  • System jobs are logged with the actor system: image.import-ready, image.import-failed, system.daily-cleanup and system.migration (a data migration script; data = { migration, dryRun, changes }).
    • 

  • Icon uploads and deletes are logged as icon.uploaded (also when the same bytes existed: data.existing = true) and icon.deleted. The two registry browse calls (repositories, tags) are GET calls and are not logged.
    • 



GET /v1/audit-log filters: action (exact, or a prefix that ends in ".", such as template.), actor (uid, e-mail or system), targetType, target, outcome (ok or error), from and to. In the console, a History button on each detail page shows that item's entries.
