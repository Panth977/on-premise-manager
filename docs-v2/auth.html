Security

Auth & access

OPM has four trust paths. People log in to the cloud with Firebase Auth. Agents sign every request with their own site key. People do NOT log in to an agent: the agent GUI only asks "Who is working right now?" and writes that email as the actor. The site never uses Firebase, so a later move away from Firebase is simple.

Access rules (cloud)

Each account has a list of access rules. The API denies a request by default. It allows the request when one rule matches. A manager of a deployment can do every deployment.* action on that deployment.

Target

Install token and enroll

An install command works for one site, one time, for 24 hours. The site config is empty after the install. Nothing runs until a person opens the agent GUI, logs in with the deployment access key, names themselves in the "Who is working right now?" popup, and approves the first proposal. The install token also gives the agent the first accessKeyHash.

The command can be seen again. While the token is active the cloud stores it, so View on the Setup page shows the command again any time (60 s, logged as install-token.revealed + audit). Regenerate revokes the old token and makes a new one. After enroll, revoke or expiry the stored token is deleted.

Agent GUI: login (access key), then "Who is working right now?"

The agent GUI has two separate layers. The login proves that the person has the deployment access key. The actor popup names the person who works now, because many people share one key and a site does not know when a new operations person takes over.

1 · Login — /_opm/login

  • One field: the deployment access key (24 characters, base32). There is no email/password and no Firebase on the site.
  • The cloud makes the key when the deployment is created. The Setup page (/app/deployments/{id}/setup) shows it masked, with View (visible for 60 s, then masked again; logged) and Regenerate. The cloud stores the key and its accessKeyHash (argon2id). Sites get only the hash.
  • POST /_opm/api/login { accessKey } → cookie opm_session (HttpOnly, SameSite=Strict, Secure on https). It expires 6 h after login. There is no sliding renewal.
  • After 6 h every API call returns 401 session-expired and the GUI goes to /_opm/login.
  • Rate limit: 5 failures in 5 min per IP → 429 rate-limited.
  • Activities: login.succeeded, login.failed { ip, userAgent }, logout.
  • The same login works on all three GUI ways (edge /_opm/, agentGuiAliasPort, agentPort). The cookie is per host and port.

2 · Actor popup — every page load

  • After login, on EVERY page load, refresh, new tab or new session: a blocking popup asks only for the email ("who is working right now?").
  • Below the field: recently used emails — from browser localStorage first, then up to 10 from GET /_opm/api/actors/recent. Click one to fill the field.
  • POST /_opm/api/actor { email } (needs a valid opm_session) → actorToken in page memory only. Its expiry = the session expiry.
  • Every write needs both: the cookie AND Authorization: Actor <actorToken>. Activities record actor.email + sessionId.
  • Activity actor.declared { email, sessionId, siteSlug, userAgent, ip }. The popup is NOT authentication.
  • Header chip: the email · "session ends in 4 h 12 m" · Change person (opens the popup, keeps the session) · Log out (ends the session).

Access key rotation

The new hash travels like every cloud fact: each agent with internet fetches it, and sites without internet get it from the peer cloud view (latest fetch wins).
  1. A person with deployment.setup.write clicks Regenerate on the cloud Setup page and types ACCEPT. The cloud makes a new key, stores it and its new accessKeyHash (+ accessKeyVersion +1), and shows the new key for 60 s. People can View it again any time later. Activity access-key.rotated + audit deployment.access-key-rotated.
  2. Each site accepts the old key until it receives the new hash. From then on, only the new key logs in on that site. So for a short time two sites can accept different keys.
  3. Sessions that are already open stay valid until their 6 h expiry. Rotation does not log people out.
  4. A site that is offline keeps the old hash until it has internet, a peer with the new cloud view, or a browser tunnel.
  5. Lost the key? Open the Setup page and click View (needs deployment.setup.write). Every view writes the activity access-key.revealed + audit deployment.access-key-revealed. Regenerate only when the key may have leaked or a person leaves.

Removed: two-phase credential renewal

What changed from the first design

The first design renewed a shared deployment credential with a two-phase commit across all sites. That is gone. The access key is simpler: only its hash goes to the sites, with the cloud view, and each site switches when it receives the new hash. Machine trust does not change: a 24 h install token enrolls the site, the site gets an Ed25519 key, and every agent → cloud and agent → agent request is signed.

Secrets: masking and reveal audit

Prototype decision

Secrets are stored like variables: plain values in the same documents (Firestore, agent SQLite). There is no Cloud KMS, no data key and no Secret Manager. Database security is out of scope for now. The protection is in the API and the GUIs.

  • Every credential stays viewable. Every credential can be viewed again and regenerated any time by a person with the permission. Both GUIs use one component, RevealValue: masked by default, View shows the value with a 60 s countdown ring, then masks it again (also on page change and when the tab is hidden). Every value response has Cache-Control: no-store, and value requests are limited to 30 per person per minute (429).
  • Values never appear in logs, diffs (diff shows "changed / not changed"), debug logs or downloaded activity bundles.
  • Snapshots contain the config with secret values. The download dialog warns about this.
  • Templates never hold secret values. A secret with generate gets a value when a person creates the deployment.

Signed requests

Agent → cloud and agent → agent requests carry four headers. The receiver rejects a request when the time is more than 60 s off, or when it saw the nonce in the last 5 min.

POST /v1/agent/heartbeat
X-OPM-Site:  acme-plant/app
X-OPM-Ts:    1791367800
X-OPM-Nonce: 3q2-7wEAAZv4mXrQ0k1yTg
X-OPM-Sig:   <Ed25519 signature, base64url>

string to sign (lines joined with \n):
POST
/v1/agent/heartbeat
1791367800
3q2-7wEAAZv4mXrQ0k1yTg
sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
  1. Hash the bodyCompute the sha256 of the raw body bytes. An empty body uses the hash of the empty string.
  2. Build the stringJoin method, path (with query), ts, nonce and body hash with a newline.
  3. SignSign the string with the private site key (Ed25519). Encode the signature as base64url.
  4. VerifyThe receiver finds the public key of acme-plant/app, checks the time window, the nonce cache and the signature.
