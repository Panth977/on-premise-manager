Safety

Backups & rollback

The agent takes a snapshot before every update. You can also take one by hand, download it, import it on another day, and roll back to it. A rollback uses the same gate as an update: all sites, a 60-second wait, and the word ACCEPT.

The snapshot record

The full type is on the Data model page. Short form:

interface Snapshot {
  snapshotId: string;            // ULID
  createdAt: Ts;
  reason: 'pre-update' | 'manual' | 'scheduled' | 'imported';
  revId: RevId; seq: number;     // the head at the time of the snapshot
  sites: { [siteSlug: string]: {
    config: Config;
    images: { serviceSlug: Slug; version: string; digest: Sha256; configDigest: Sha256 }[];   // loaded as :
    volumes: { volumeSlug: string /* the declared site volume (pre-D snapshots: name) */; containers: Slug[] /* containerSlugs that mount it */; sizeBytes: number; sha256: Sha256; path: string /* sites/<site>/volumes/<volumeSlug>.tar.zst */ }[];
    sizeBytes: number;
  } };
  createdBy: string;             // email, or "system"
  note: string;
}

Site volumes: what gets backed up

Data folders are declared on the site (template or deployment → site → Volumes; agent GUI → Config › Volumes). Each one is a SiteVolume { volumeSlug, label, description, backup, location, kind, seed } and lives on the site server at its location: auto = <agentHome>/volumes/<volumeSlug>/ (agentHome = the agent data dir, default /var/lib/opm), or a custom path (./… = relative to agentHome, or absolute). A volume is backed up WHEREVER its location is. A container mounts a volume by picking it in its Volumes section; several containers may share one. So the agent knows exactly what to back up: the declared volumes with Back up on.

Mount sourceBacked up?
Declared site volume, Back up on (default)Yes — once per volume, even when several containers share it
Declared site volume, Back up offNo (for caches or data you can rebuild)
Host path (advanced)Never — the GUIs say so
File, secret, "Not mounted"Never (files and secrets come from the config; rendered files are rendered again on restore)
Orphan folder (a volume removed from the config)Never; the folder stays on disk and is never deleted automatically

The agent GUI Backups page shows, per site, the agent home and a volumes table (from GET /_opm/api/sites/{siteSlug}/volumes): name, label, the absolute folder on the server, size on disk, Back up on / off, used by (container → mount path), last snapshot that contains it. Orphan folders are listed greyed ("not declared — kept on disk, never backed up") and host-path mounts are listed with "never backed up".

Single-file volumes

A volume is a folder by default. Choose Single file when the container needs one data file at a file path, for example /app/runtime.json. The agent creates an empty file at the location before the container starts. A single-file volume is backed up and restored like a folder (one file).

  • Mount it at a file path. A path that ends with / is an error (V_VOLUME_KIND).
  • On an image volume, the kind must match what the image keeps there — every image volume has a kind, Folder or File, set on the image page (ImageVolume.kind):
    • single-file volume on a File image volume (e.g. flow → /data/flows.json): valid, no warning;
    • single-file volume on a Folder image volume: warning V_VOLUME_KIND_IMAGE — pick a folder volume, or set the image volume to File on the image page if the path is a file;
    • folder volume on a File image volume: error V_VOLUME_KIND_MISMATCH — pick a single-file volume, or set the image volume to Folder.
    The container page shows one-click fixes next to the message: + New single-file volume… / + New folder volume… (the volume drawer with that kind) and Set image volume X to Folder / File on the image page.
  • Mounted read-write, a single-file volume shows the info V_FILE_VOLUME_RENAME once per mount (see below). Read-only mounts do not.
  • The kind is fixed after the volume is created. For another kind, make a new volume.
Node-RED and other apps that save with "write a temp file, then rename"

Apps that save by writing a temp file and renaming it (e.g. Node-RED flows.json) need a folder volume — a single-file Docker mount breaks on rename. Use a folder volume with its own content instead. (Tested: the rename fails with "Device or resource busy".)

Recommended for Node-RED
  1. Volumes page: add a Folder volume nodered-data, open its Content and create (or upload) flows.json and settings.js right there.
  2. Container page of node-red: mount nodered-data at /data (the image volume /data, or + Extra mount /data), read-write. Leave the File image volumes flow / settings on Not mounted.
  3. Turn on Persist to cloud for nodered-data when flows change on the site and you want to see, edit and send them from the cloud (see below).

Never mount a Config file inside /data: Files are static and read-only and are never mounted on a writable volume (error V_FILE_IN_WRITABLE_VOLUME).

Volume content (starter content)

A volume can start with content: its own file tree, edited in the cloud console (template or deployment → site → Volumes → a volume → Content). Files (the Files page) are never volume content — they are static, read-only files mounted as single files.

  • File tree: new file, new folder, rename, move (drag and drop, or Move to…), duplicate, delete, upload files or whole folders from your computer.
  • Editor: code editor with highlighting by extension (JSON, JavaScript, TypeScript, YAML, conf / ini, shell, HTML, CSS, Markdown …). Binary files and text files over 2 MiB show their size and a download link.
  • Per file: mode (0644, 0755 for scripts …) and Render {{ }} — on: the file is a template, rendered once per site when it is written (like a File with expressions); off (default): written byte for byte.
  • Limits: a file ≤ 50 MiB; ≤ 1000 files, ≤ 1000 empty folders, ≤ 200 MiB in total.
  • Single-file volumes have one file of content instead of a tree. A .tar.gz archive (folders, ≤ 200 MiB, never rendered) is still accepted.
  • The bytes are stored in the cloud by their sha256; the configuration holds only the list (path, sha256, size, mode), so the Diff before publishing lists every changed file with a text diff.
  • The agent writes the content only once: when the volume is new or empty, during the update, before the containers start.
  • After that the volume is marked "seeded". The site owns the data. Changes on the site (for example a new Node-RED flow) are kept.
  • A later change of the content does not touch existing data. The review says "starter content — written only into new / empty volumes". To change live data, use Persist to cloud (below) or the volume manager.
  • Revisions that use volume content or Persist to cloud need agent 0.12.0 or newer on the site; the publish dialog warns per site.

Reset to starter content

To start a volume again from its starter content, open the agent GUI of that site → Backups → volumes table → Reset to starter content…. The button is there only for volumes with starter content, and only on the site's own agent GUI.

  1. Click Reset to starter content…. Wait 60 seconds (you can cancel).
  2. Type ACCEPT and confirm.
  3. The agent takes a snapshot of this volume first (note "before reset of <volume>").
  4. It stops the containers that use the volume, empties the volume, writes the starter content and starts the containers again.
  5. The result shows the number of entries written and the snapshot. To undo, roll back to that snapshot.

Activities: snapshot.created, volume.reset-to-seed, volume.seeded.

Persist to cloud

For volumes whose content changes on the site and that you want to keep, review and edit in the cloud — Node-RED flows, client integration code — instead of a git repository. Turn it on in the volume's Content page (folder volumes only) and publish.

SettingDefaultMeaning
Excludenode_modules/ .npm/ .cache/ *.logNever sent to the cloud and never changed by an apply. name/ = folders, *.log = any file name, a pattern with "/" counts from the volume root, ** = any folders.
Size cap50 MiB (1–200 MiB)A snapshot over the cap is refused (the error lists the biggest files — exclude them). Files over 24 MiB, links and special files are skipped and listed.
AutomaticonThe agent checks the volume every minute and takes a snapshot 2 minutes after the last change (at most every 15 minutes).
  1. Site → cloud. Every snapshot becomes a new version in the cloud (history: who / what / when, files added, changed, removed). Snapshots happen automatically, on Snapshot now (cloud or agent GUI), before and after every apply. If the cloud cannot be reached, they wait on the site and upload later.
  2. Edit in the cloud. Deployment → site → volume → Cloud copy: the same editor on the latest version. Save as new version. Any version can be restored (it becomes the latest) or copied into the starter content.
  3. Cloud → site. Send to site… (choose the version, "restart the containers that use it"). Nothing changes on the site yet: the agent GUI shows Cloud ahead; a person on the site opens Docker › Volumes → Apply cloud version, waits 60 s (⏩) and applies. The site does not need to be online when you send.
  4. Conflicts. If the volume changed on the site since the snapshot your edit started from, the agent shows Conflict and asks: Overwrite (the cloud version wins), Keep live (nothing is written; the live content is uploaded so you can see it) or Per file (changes on one side are merged; for files changed on both sides you choose, with a diff). It never overwrites silently. Before writing it takes a Backups snapshot of the volume.

Agent GUI states: In sync · Live changed · Cloud ahead · Conflict · No snapshot yet · Waiting to upload · Error. Activities: volume-content.snapshot, …snapshot-uploaded, …version-created, …sent, …conflict, …applied, …kept-live.

Free-space rule

Before every snapshot, the agent estimates the size from the volume sizes. If the free disk space is less than 1.2 × the estimate, the snapshot fails. For a pre-update snapshot, the update then stops before any change.

Roll back to a snapshot

  1. PickOpen /_opm/app/backups and select a snapshot. The page shows what changes (see the planner below).
  2. GateThe "Roll back" button shows only when every site is reachable over the mesh and no update runs.
  3. ConfirmClick Roll back. Wait 60 s. Type ACCEPT. The dialog says that data written after the snapshot is lost, and it shows the declared actor (the email from the "Who is working right now?" popup), which goes into the activity.
  4. Snapshot firstThe agent takes a pre-update snapshot of the current state, so you can undo the rollback.
  5. RestoreOn every site: the snapshot config, the snapshot images, the snapshot volumes. Volumes are restored by volumeSlug into their location (default <agentHome>/volumes/<volumeSlug>/), whatever container mounts them now (a volume moved to another container keeps working). Volumes that are not in the snapshot are left as they are. Restart in depends order. Verify every container.
  6. New revisionA new revision becomes head: origin: "agent", summary: "rollback to 01J9Z4… (seq 3)". History is never rewritten.

Download: the .opmsnap file

One file holds the snapshot of every site. It is a tar archive.

Path in the archiveContent
manifest.jsonThe Snapshot record, plus the sha256 and size of every other part.
sites/<siteSlug>/config.jsonThe config of that site at the snapshot.
sites/<siteSlug>/volumes/<volumeSlug>.tar.zstOne archive per backed-up site volume (a volume shared by several containers is archived once). Host paths, back-up-off volumes, files, secrets and rendered files are not archived. Older snapshots name the volume name; it is read as the volumeSlug.
images/blobs/sha256/<hex>Only with "include images": the image layers and manifests.
signature.sigEd25519 signature of manifest.json by the site that made the download.

Import

  1. Upload/_opm/app/backups → "Import snapshot" → choose the .opmsnap file.
  2. Check the signatureThe signature must belong to a site of this deployment.
  3. Check every partThe sha256 and size of every part must match the manifest. One error rejects the whole file.
  4. Check the imagesEvery image digest must be on the sites, in the file, or in the cloud catalog.
  5. List itThe snapshot shows with reason imported. You can roll back to it with the normal gate.
