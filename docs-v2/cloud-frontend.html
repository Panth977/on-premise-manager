Cloud frontend

Cloud frontend: every route

Agent 0.14.1: one action — Commit (SPEC §21 #105)

There is no working copy and no draft any more. Every edit stays in your browser (kept in local storage, so a reload loses nothing) until you press Commit… and give a message — that writes the commit directly. The bar on every config page shows N changes (not committed) · Discard · Review · Commit…; drawers and dialogs Apply into it, there is no Save button. If someone else committed meanwhile, your changes are rebased onto the new head (automatically when nothing conflicts). On a site, a Commit in the agent GUI also applies the changes to the containers (a failed apply writes no commit); there, "uncommitted" means only changes made on the server outside the agent — commit those first. Details: branches-commits.md §15.

Agent 0.15.1: one Commit = one transaction, including the files (SPEC §21 #107)

Editing a file — a volume's starter content (create, edit, rename, move, delete, upload files or folders), a File's content, a volume archive — is a pending change like any other: nothing is uploaded while you edit and there is no Apply or Save content button. The bytes stay in your browser (memory + IndexedDB, so a reload restores them too) and the change bar counts every file; Review shows a per-file diff. Commit… first uploads only the new files to a staging area ("Uploading 2 of 5 files · 1.2 MB of 3 MB"), then writes the commit; the server checks every file, moves it into the store and only then makes the commit visible. If anything fails — an upload, validation, someone else committed first, the network — nothing is committed, the staged files are deleted and your changes (files included) stay in the browser so you can retry. Drafts: everything you have not committed is auto-saved in this browser (IndexedDB) per account; after a refresh or when you come back you are asked “You have unsaved changes from <time> (N changes) — Restore or Discard?”. A draft is only offered when it was made on the current latest commit — otherwise it is discarded with a notice. Drafts expire 1 hour after the site was last open in any tab (an open tab keeps them alive) and are deleted when you log out. Details: branches-commits.md §16.

§21 #106: Admin → GitHub

/app/github (admins): repository + Mirroring toggle, token (masked, View 60 s, Replace…, Remove), Test connection, branch status table with Sync / Sync now / Resync everything. Template and deployment create forms show the slug (the GitHub branch name; immutable). See github-mirror.md.

Agent 0.14 / §21 #104: History, Compare, Agent branches

Template and deployment scopes have History (commits; open, compare two, revert, reset) and Compare (any branch → this one: cherry-pick items, conflicts, "Removed by this merge", then Merge… with a message). Diff and Template sync redirect to Compare. Every config page shows "N uncommitted" and Commit…. New template / deployment can start from a template, a deployment or an agent branch. The deployment Agent branches page shows each site (behind / ahead / differs, drift). See branches-commits.md.

Site pages: Edge

Every site (template site and deployment site) has the page Edge (…/sites/{siteSlug}/edge). Open it in the prototype: Templates → a template → sidebar app → Edge (the prototype still shows the older route drawer and "first match wins" order; the cards below describe the current page). It edits SiteConfig.edge (see Edge). The agent runs it with an embedded Caddy server (agent edge).

1 · Ports, limits, hosts

  • HTTP port, HTTPS port, Max request body (unlimited or a size).
  • Add a hostname: DNS name, wildcard *.acme.com, IP, or *.
  • TLS mode per host: none · internal · acme (email, challenge, DNS provider + token secret) · files (cert file + key secret).
  • HTTP→HTTPS redirect per host.
  • Response headers → browser per host (nginx add_header in a server).
  • Certificate status from the last agent report.

2 · Routes (nginx rules)

  • The table shows the effective order: exact, prefix with stop regex, regex, prefix (longest first). A badge says why. Only regex rows have ↑ / ↓.
  • + Proxy route, + Redirect route, + Rewrite route and Edit open the route page (…/edge/route?id=…): match (prefix / exact / regex, stop regex, hosts, methods), action, connection (WebSocket, streaming presets SSE / Uploads, body limit, timeouts), Request headers → container, Response headers → browser, and a Try a path box.
  • A response header put in the request group (for example Cache-Control: public, max-age=3600) shows a warning with Move to response headers.
  • Import from nginx.conf… opens …/edge/import (how).

3 · Test a URL

  • Enter a URL, a method, optionally a body size and "WebSocket upgrade". The box shows the host, the winning route in the effective order, rewrite steps, regex groups, the redirect target or the container URL and path.
  • It lists the request headers sent to the container and the response headers sent to the browser (from the route or the host), timeouts, buffering, body limit, WebSocket.
  • Tick "not ready" to see the 503 page. Errors block Save; warnings do not.

The rules (matching, rewrites, variables, headers, streaming, timeouts) and the nginx compatibility matrix are on Networking → Edge routing.

Draft only

The Edge page changes the cloud draft like every other field. The agent validates the edge again in staging and reloads Caddy in the apply step. A failed reload keeps the old edge running and fails the update (automatic rollback).

Containers: the full-page editor

A container is one instance of an image on a site. One image can run many times on the same site, each time with its own name, env, ports and volumes (for example worker and worker-2 from northwind-backend:v1, one with NODE_ENV = worker and one with NODE_ENV = pg-listen). Open it in the prototype: Templates → a template → sidebar app → Containers → + Add container, or a container name in the tree.

Routes

  • + Add container opens the full page …/sites/{siteSlug}/containers/new (no modal).
  • A row opens …/containers/{containerSlug}.
  • Duplicate opens …/containers/new?duplicate=<containerSlug>: a copy with a new suggested name, host ports cleared, a <old>-<volume> volume renamed to <new>-<volume> and declared on the site.
  • The same page exists on the deployment draft: /app/deployments/{deploymentId}/sites/{siteSlug}/containers/….

1 · Service + name · 2 · Ports

  • Service and Version pickers (any service, also one that is already on the site).
  • Name (containerSlug): suggested as the service slug, then -2, -3 …; editable only while new; unique on the site; not new. It is the DNS name, the name in expressions and in edge routes.
  • Ports: one row per image port: Published toggle, host port (number or {{ }}), bind address (0.0.0.0 all · 127.0.0.1 this machine), Edge may proxy toggle.

3 · Volumes · 4 · Env · 5 · Runtime

  • One row per image volume ("image volume data · /var/lib/cassandra") with ONE grouped dropdown: Data volumes (the volumes declared on the site, "shared with X" when another container uses one, and + New data volume…), Files, Secrets, Advanced: host path…, Not mounted. Read-only toggle only for volume / host (off = read-write); file / secret show a "read-only" badge. Column Inside the container: volume / host rows show the mount path (the image path by default); file / secret rows show the text "mounted read-only at <path>" — WHERE the file lives on the server is set on the Files page, not here. Edit path opens the expression input (Reset = the image path). A file / secret / volume that other containers also mount shows "shared copy · also used by X, Y". An image volume with no choice shows "Not mounted — pick a data volume". Each image volume shows its kind badge Folder / File (set on the image page); a mismatch is explained with the exact control to change and one-click fixes: folder volume on a File → error V_VOLUME_KIND_MISMATCH with + New single-file volume… and Set image volume X to Folder on the image page; single-file volume on a Folder → warning V_VOLUME_KIND_IMAGE with + New folder volume… and Set image volume X to File on the image page (opens /app/services/S/image/V?volume=X: the row is outlined, a banner explains, "Back to the container"). A read-write single-file volume shows the info V_FILE_VOLUME_RENAME (save-by-rename apps such as Node-RED fail with EBUSY) with the tip Recommended for Node-RED. "+ New data volume…" on an image volume starts with that image volume's kind. + Extra mount.
  • Env: the image env list with defaults; a choice env is a dropdown, a secret env a secret picker, values accept expressions with autocomplete.
  • Runtime: command / entrypoint, restart, depends (other containers of this site; the site depends are shown with a link), CPU / memory limits, health check override.
  • A sidebar shows the name, image, published ports, Mounts lines ("/etc/app.json ← file web-config (server: ./config/web.json)", also volume / secret / host) and the live validation issues of this container.
Site host is optional

The site form has Host: Auto-detect (recommended), on by default (host: null). The agent reports its address after the install, and the table shows "auto" (and the address once known). Turn it off only to set a DNS name, a NAT address or {{ var.… }}. An optional host variable without a value shows the warning V_HOST_AUTO in a deployment and the site uses its auto address; it never blocks a save or a publish. A required variable is set at deployment: in a template it shows "set at deployment" and no warning.

Files with expressions

A text file has the toggle Resolve {{ }} expressions (on by default; binary files: always off). The code editor highlights {{ }} blocks, completes paths (var, secret, site, self, deployment — not container.* / file.*: a file is rendered ONCE per site and shared by every container that mounts it, "use a variable instead"), checks the content while you type (errors at line:col) and reminds you that a literal {{ is written {{ "{{" }}. Preview for site… asks for a site and shows the rendered file with secrets as •••. The Files table has the column On the server ("auto · <agentHome>/files/<slug>" or the custom path) and the file drawer the control Location on the server: Auto (recommended) / Custom path ("./ = agent home", or an absolute path). The content loads from GET /v1/blobs/{sha256} (direct for ≤ 8 MiB, else a signed URL). A failed load shows the real reason, for example "download failed: 403 …" or "network error / CORS", never only "Failed to fetch".

Site pages: Volumes

A site declares its data folders once, on …/sites/{siteSlug}/volumes (SiteVolume). Containers then pick one in their Volumes section. The agent knows exactly what to back up: the declared volumes with Back up on (Backups).

Volumes table

  • Columns: Name (volumeSlug) · Label · Description · Kind (folder / single file) · Starts with (starter content) · On the server ("auto · <agentHome>/volumes/<slug>" or the custom path) · Back up toggle · Used by (container chips, each opens the container page) · Edit / Delete.
  • Info line: "Volumes are folders on the site server (auto: <agentHome>/volumes/<name>). Back up = included in snapshots. Host paths are never backed up."
  • A volume that no container uses shows the warning V_VOLUME_UNUSED.

Add / edit (side drawer)

  • Name (volumeSlug, ^[a-z0-9][a-z0-9_.-]{0,99}$, unique on the site; fixed after create) · Label · Description · Kind: Folder / Single file (fixed after create; Single file shows the rename warning for Node-RED-like apps) · Starter content: Empty / Own content (opens the content page) / Archive (.tar.gz ≤ 200 MiB) — Files are never volume content (§21 #101); written only into a new or empty volume (how) · Back up (on by default) · Location on the server: Auto (recommended) / Custom path ("./ = agent home", or absolute; V_LOCATION).
  • The same drawer opens from a container page with + New data volume…, prefilled <container>-<imagevolume> (then -2 …); it declares the volume and selects it.
  • Changes go into the browser change set and are committed with Commit… (§21 #105).

Volume content page (§21 #101)

  • Route …/sites/{siteSlug}/volumes/content?volume=<slug>&tab=content|persist|cloud (template and deployment scope; a full page, not a drawer).
  • Starter content: file tree (folders first; new file / folder, rename, Move to… and drag-and-drop, duplicate, delete; right-click menu; keyboard: arrows, Enter, F2, Del) + upload of files and folders (relative paths kept; existing names → Overwrite / Skip / Keep both) + CodeMirror editor by extension, per-file mode and render {{ }}; binary or > 2 MiB files show size + download. Limits: 50 MiB per file, 1000 files, 200 MiB. Save uploads the changed blobs, then saves the site. Single-file volumes: one editor.
  • Persist to cloud: on / off, exclude patterns (live check + preview of what they leave out), size cap 1–200 MiB, automatic snapshots.
  • Cloud copy (deployment, persist on): state badge (In sync / Live changed / Cloud ahead / Conflict / No snapshot yet / Waiting to upload / Error), Latest version in the same editor → Save as new version (409 "a newer version arrived": Compare / Reload), History (origin, trigger, restored from, who, when, counts, per-version diff), Restore, Send to site… (version, restart containers, note; warns when the site's agent < 0.12), Cancel pending push, Snapshot now, Use as starter content.
  • A legacy starter content that references Files shows an error card with Convert to own content; a File mounted inside a writable volume (V_FILE_IN_WRITABLE_VOLUME) has Move into the volume's content on the container page.
  • Diff: per-file content changes (<site>/volumes/<v>/content/<path>) with View diff; the publish dialog warns per site whose agent is older than 0.12.

Delete

  • A volume that a container uses cannot be deleted: the dialog lists the containers (links).
  • An unused volume: confirm. The folder stays on the server (it becomes an orphan; never deleted automatically).
  • Errors V_VOLUME_UNDECLARED (a mount names an undeclared volume) and V_READONLY (a file / secret mount not read-only) block Save; they show on the row and in the summary sidebar.

Site pages: Dev tools (presets)

Every site has the page Dev tools (…/sites/{siteSlug}/devtools, template and deployment scope; sidebar node after Volumes with the preset count and an error / warning badge; SPEC §17, §21 #97). It edits the site's dev-tool presets, SiteConfig.devTools (DevToolPreset): connections the agent GUI lists ready to use under Dev tools (HTTP client, PostgreSQL, SQLite, Cassandra, Redis, MQTT). Operators can always add manual connections on the agent too; presets just save them the typing. Open it in the prototype: Templates → a template → route Site · Dev tools in "Open route".

Presets table

  • Info banner: "The agent GUI lists these presets ready to use under Dev tools. Credentials: a secret (recommended), a container env, an expression, or a typed Value (stored in plain text in the config: use a secret for production). Operators can always add manual connections on the agent."
  • Columns: Preset (kind icon, name, p:<slug>, description, read-only badge) · Kind · Target ("postgres:sql", "10.0.0.12:5432", "volume data → app.db") · Auth ("user postgres · password: secret pg-password · db acme") · Edit / Duplicate / Delete (confirm).
  • Issues from validateSiteDevTools (V_DEVTOOL_*) inline on the row and in the site validation card; errors block Save.

+ Add preset (drawer)

  • A kind picker (6 kinds), then a drawer. Preset: name, id (slug, suggested from the kind, fixed after create), description, read-only.
  • Connect to (allowed per kind): a container + port picker from the image's ports (the default port of the kind preselected) · host : port · http(s) base URL · SQLite: a declared folder volume + relative path, or a container + path.
  • Authentication per kind (PostgreSQL user / password / database, Cassandra user / password / keyspace, Redis ACL user / password / db 0–15, MQTT user / password / client id, HTTP basic / bearer / API key). Password / token = None · Value (§21 #103: typed, masked input with a show / hide toggle and the amber note "Stored in plain text in the config — anyone who can read the config sees it; use a secret for production."; saved as { kind: 'literal', value }, warning V_DEVTOOL_LITERAL, never shown in clear in Diff / Template sync, needs agent 0.13.1) · Secret (picker + "+ New secret…") · Container env (§21 #99, when the target is a container: a picker of that container's env, {{ containers.<c>.env.<NAME> }}) · Expression.
  • Expressions (field devtool): typing {{ lists the roots; pick containers. → containers.postgress. → env. → POSTGRES_USER (values shown, secrets masked); the preview shows the resolved value. With a container target, chips Use env POSTGRES_USER of postgress (PostgreSQL POSTGRES_USER / PGUSER, POSTGRES_PASSWORD / PGPASSWORD, POSTGRES_DB; Redis REDIS_PASSWORD; Cassandra CASSANDRA_USER / CASSANDRA_PASSWORD / CASSANDRA_KEYSPACE; MQTT MQTT_USERNAME / MQTT_PASSWORD …) fill a field in one click. A password from a plain (non-secret) env shows the warning V_DEVTOOL_PLAIN_ENV; an unknown env name is the error V_DEVTOOL_ENV.
  • Options per kind: SSL mode, consistency, TLS (+ skip verify, server name), timeout, rows per page, scheme / base path / follow redirects / default headers, MQTT clean session / keep alive.
  • Duplicate opens the drawer as a new preset (<slug>-copy).

Save, diff, sync, publish

  • Changes go into the browser change set and are committed with Commit… (§21 #105). Removing the last preset deletes the key: the config never holds devTools: [].
  • Diff: tab "Dev tools", one row per preset (path <site>/devtools/<presetSlug>, added / removed / changed) with a one-line summary above the JSON; credentials are expressions, so values are shown.
  • Template sync: group "Site X · Dev tools", a keyed list by presetSlug (theirs / ours / same / conflict, like volumes).
  • A local proposal on the site cannot change presets (V_LOCAL_DEVTOOLS).
Presets need agent 0.11.0 on that site

An agent older than 0.11.0 drops the unknown devTools key when it re-hashes a revision, so the hash does not match and that site refuses the revision. The Diff page (banner), the Publish dialog and the site's Dev tools page warn for every site of the draft that has presets and whose last reported agent version is below 0.11.0: "Site X runs agent <v>; dev tool presets need agent 0.11.0 or newer — upgrade the agent first, otherwise the site refuses the revision." (with a link to Setup). The warning is advice; it never blocks Publish. A site that never reported a version shows no warning. Revisions without presets stay hash-identical for old agents.

§21 #99: a preset that uses {{ containers.<c>.env.<NAME> }} needs agent 0.11.1; for a site on 0.11.0 the same places warn "Site X runs agent 0.11.0-…; a preset uses a container env ({{ containers.redis.env.REDIS_PASSWORD }}), which needs agent 0.11.1 or newer — upgrade the agent first, otherwise the site refuses the revision." (advice, never blocks).

Setup: agent upgrades

The agent upgrades from the console (SPEC §17.3, §21 #90). Nobody has to log in to the server. It is never automatic: a person clicks, and the request is logged (audit deployment.agent-upgrade-requested, activity agent.upgrade-requested).

Version and badge

  • Setup and Status show per site installed / latest (latest = the pinned release) and a badge: upgrade available · up to date · queued (requested by, when) · upgrading: download 62 % / verify / swap / restart / health · failed · rolled back (the error in a tooltip).
  • The latest version opens its release notes.

Upgrade agent · Upgrade all

  • Upgrade agent: a confirm with from → to, the notes, "the agent restarts, the containers keep running, it rolls back by itself if not healthy within 60 s", and the typed site slug. A queued request has Cancel request until the agent starts it.
  • Upgrade all (N): typed UPGRADE; one site at a time in site order; the next site starts only when the previous one is done; the first failure stops the run. A run panel shows each site; Cancel run.

Hard fallback + unattended install

  • When an upgrade from here or the agent GUI cannot run, or you need a downgrade: rerun the site's install command on the server. It asks "Installed A → available B: UPGRADE | DOWNGRADE | SAME", keeps agent.json, the key, the data and the enrollment, backs up the database, and rolls back by itself if the new agent is not healthy within 60 s (details).
  • The install command row has a disclosure Unattended install (no terminal prompts): Answer yes to every prompt (OPM_YES=1) and Docker when missing Ask / Install / Skip (OPM_INSTALL_DOCKER=1|0). The flags go after sudo. The command line says "Asks before installing Docker 28.5.2 when it is missing (uses your existing Docker ≥ 20.10 without asking)".
  • An expired or revoked token prints what to do and changes nothing.

Older agents (below 0.10.0)

  • The button is disabled. The hint says: run the site's Upgrade / reinstall command once. It sits right in the hint: View shows it for 60 s (logged), Copy, Regenerate…. Example: a server on 0.7.2, where sudo opm-agent upgrade says "unknown command".
  • After that one rerun, upgrades are a button here, or on the Agent page of the agent GUI.

Forms: icons, pickers, overlays

These rules apply to every form of the cloud frontend. Open the examples in the prototype: Services → + New service, a service → + Register image, and Registries → Test login.

Icon picker

  • Services, templates and tags use the icon picker. Accounts and deployments use it for the avatar and the logo.
  • Tab Icons: search the curated Lucide set (350 icons in groups). A pick stores lucide:<name>.
  • Tab Uploads: the icon library of the cloud. Upload a PNG, SVG or WebP file (≤ 64 KiB), or reuse an icon that is there. A pick stores upload:<iconId>. The same file again gives the existing icon.
  • None stores null: the app shows the default icon of the entity type.
  • Delete an upload only when nothing uses it (409 conflict lists the users).

New / edit service (one modal)

  • Fields: Label, Name (id), Icon, Description. There is no repository field.
  • The form makes the name from the label (lower case, "-"). You can change it before you save. After create it is fixed.
  • The name is the only identifier of the service (serviceSlug): the document id and the image name on a site (<serviceSlug>:<version>). It is the suggested name of a new container; the DNS name and the name in expressions are the container name (containerSlug).

Register image

  • Version: the OPM name of the image (v1, v2, …). The form suggests the next version. It is the document id and it is fixed.
  • Image reference: one combobox for the full docker reference. It completes registry → repository → tag and shows the parsed parts as chips (host, repository, tag, digest).
  • Registry: matched by the host of the reference. No match = public (no credentials). You can choose another registry.
  • Clone from… copies the fields of a version. Read from registry shows a diff; nothing changes until you choose.
  • Env: free text or choice (1–50 options; the default is one of them). An old list default opens as a choice.
  • Mount path: may hold expressions, for example /app/helper/config/env/{{ container.env.NODE_ENV }}.ts. It must start with a literal "/" (else V_PATH).

Image detail

  • Clone as new version opens Register image with all fields of this version.
  • While the import failed, Edit source changes the reference and the registry. Then Retry import. In other states the source is locked.
  • The site image name is <serviceSlug>:<version>, for example northwind-backend:v1.

Registries

  • Anonymous: username and password stay empty. Use it for public images that need a mirror or a host match.
  • Test login takes an optional repository. With a repository the test also checks the pull access.
  • Docker Hub gives a token also without pull access. The cloud reads the access claim of the token and shows: "repository X not found, or account Y has no pull access to it".

Pickers and overlays

  • Pickers rule: a field that refers to a thing that exists (service, version, registry, repository, tag, icon, variable, secret, file, site, container, port, site volume, not-found page) is a picker. Free text is only for labels, descriptions, paths, hostnames, HTML and values.
  • Overlay rule: every overlay (modal, drawer, menu, combobox list, tooltip, toast) renders at document.body. All overlays use one z-index scale. The top overlay gets Esc and the focus trap.

One form per entity (shared with the agent GUI, §21 #102)

Every form that the agent GUI also shows comes from the shared package ui/ ($opm/forms/…): container, edge host / route / ports / nginx import / Test a URL, variable, secret, dev-tool preset, volume, persist settings, site settings, file definition and the transfer send form. The cloud renders it for create and edit; read-only users get the SAME form disabled. Locked fields show a lock icon with the reason (for example "Fixed after create"). Services use one modal and deployments one drawer for both create and edit. The site editor's Discard / Save live in the sticky change bar at the bottom (the same bar as the agent's local-edit bar). Details, the comparison with other Docker GUIs and side-by-side screenshots: gui-consistency.md.

Rules for every screen
  • The frontend calls only the HTTP API https://api.opm.example/v1/… with the Firebase ID token. It never reads Firestore or Storage directly.
  • A screen hides the actions that the user has no permission for. The API checks the permission again.
  • Edits in the deployment scope change the cloud draft only. The sites change only after a person approves the proposal in the agent GUI.
  • Every entity has one identifier, and the routes use it: {serviceSlug}, {version} (of an image in its service), {registryId}, {templateId}, {tagSlug}, {deploymentId}, {siteSlug}, {containerSlug}, {uid}, {iconId}. new is reserved (…/containers/new), so no container can be named new.
