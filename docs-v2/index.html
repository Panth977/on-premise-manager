On-Prem Manager (OPM)

New in 0.15: GitHub mirror + docker compose without the agent

Every template, deployment and site branch is mirrored into a GitHub repository (Admin → GitHub), and every git branch runs as docker compose up per site without the agent. Read github-mirror.md.

New in agent 0.14: branches and commits

Templates, deployments and sites are branches; compare and cherry-pick between any two; no proposals; manual server changes are detected. Read branches-commits.md.

OPM installs and manages container applications on client servers. The operations team works in a cloud dashboard. On each client server, an agent runs the containers. Nothing changes on a server until a person on site approves it. OPM has no knowledge of any specific application: services, images and setups are data.

The 11 core rules

1 · One config for all sites

A deployment has one config: variables, secrets, files and sites. Every site keeps the same copy. One approval covers all sites.

2 · The agent never sees registry passwords

The cloud imports images from the registries. The agent gets image layers only from the cloud catalog.

3 · Nothing runs until approved

After install, the site config is empty. The first setup is a proposal like every other change.

4 · Approve = all sites ready + 60 s + ACCEPT

The Approve button shows only when every site is reachable and staged. After a click, wait 60 s, then type ACCEPT.

5 · Snapshot first, roll back on failure

Every update starts with a snapshot on every site. If any step fails, all sites roll back to it.

6 · Local edits, except containers and images

On site, you can change values, files, ports and more. Only the cloud can add or remove containers or change an image version.

7 · The cloud never merges silently

A proposal must use the current head as its parent. If the head moved, the proposal is stale. Rebase it on the Diff page.

8 · Activities are append-only

Each site keeps a hash-chained activity log. Uploads are upserts: an existing record never changes.

9 · Site login with the access key, then "Who is working right now?"

Sites do not use Firebase. The agent GUI login takes the deployment access key (the cloud Setup page shows it with View any time and can regenerate it; the sites get only its hash). The session ends 6 h after login. After login, on every page load, the GUI asks for the email of the person who works now and logs every action with it.

10 · The edge is in the agent (embedded Caddy)

The agent routes user traffic itself: Caddy v2 runs inside the agent process (not a child process, not a container) on 80/443, with proxy, strip prefix, redirects, many hostnames and automatic TLS. Containers do not publish 80/443. The mesh uses agentPort 7080; the GUI is also on agentGuiAliasPort 8080. Outbound traffic goes only to api.opm.example:443 (and the ACME server for public certificates).

11 · Each agent fetches on its own, peers share

Every agent with internet polls and downloads by itself. Sites exchange their cloud view every 10 s: the latest fetch wins. Blobs come from a peer first; one fetcher per blob gets the rest from the cloud.

12 · No internet? Use a browser tab

Route order for cloud calls: own internet → a peer → the browser tunnel. A person opens /_opm/app/internet and clicks Start. Only one tab per site; revoke the old tab first.

Glossary

TermMeaning
DeploymentOne on-prem installation for one client. It has 1 or more sites. Example: acme-plant.
ContainerOne instance of a service image on a site. Identified by containerSlug (its name and DNS name on the site network). One service may run as several containers on one site, each with its own env, ports and volumes.
TransfersAgent 0.11.2: one Transfers page per site in both GUIs (Send left, Receive right). Store-and-forward both ways — nobody has to be on the other end: the agent queues sent files and uploads them when the cloud is reachable, and fetches cloud files whenever it is online. Send › Path picks any file on the server through a filesystem picker with a safety policy. See Transfers.
Dev toolsAgent 0.11.0: service GUIs in the agent GUI — HTTP client, PostgreSQL, SQLite, Cassandra (CQL), Redis, MQTT — whose queries the agent runs on the site server. Connections are presets from the cloud (SiteConfig.devTools; credentials as a secret, a container env, an expression or — agent 0.13.1, §21 #103 — a typed Value kept in plain text in the config) or manual ones made on the site; every execution is logged (devtools.query, redacted). See Agent GUI → Dev tools.
SiteOne server that runs one agent and a set of containers. Identified by siteSlug (for example app, db).
AgentThe opm-agent binary on a site. It runs containers, the edge and the agent GUI.
ServiceA named kind of container, for example postgres. Its only identifier is its serviceSlug. It has images.
ImageOne version of a service (for example v1), imported from a full docker reference into the cloud catalog. Its content never changes. On a site it is named <serviceSlug>:<version>, for example northwind-backend:v1.
TemplateA reusable blueprint: variables, secrets, files and sites. A deployment copies a template or starts empty.
ConfigThe deployment-wide document { variables, secrets, files, sites }. The same on every site.
DraftThe config that the cloud edits. It reaches the sites only through a proposal.
RevisionAn immutable version of the config. Revisions form one linear chain on the sites.
HeadThe revision that all sites run now.
ProposalA revision that waits for approval in the agent GUI (/_opm/app/updates).
StagingAutomatic preparation on each site: validate, download layers and files, load images, dry run.
GateThe conditions that show the Approve button: parent = head, all sites reachable, all sites staged, no other update running.
CoordinatorThe agent that runs a deployment-wide operation (update, rollback) on all sites.
Site volumeA data folder declared on a site (volumeSlug, label, description, Back up on / off). Containers mount it by name; several may share one. On the server: its location (auto = <agentHome>/volumes/<volumeSlug>/, or a custom ./… / absolute path).
agentHomeThe agent data dir on a site (default /var/lib/opm). A location written ./x/y is relative to it. Each site keeps ONE copy of every file, secret and volume there (or at a custom location); containers share those copies.
SnapshotA backup taken by the agent: config, image refs and the site volumes with Back up on (host paths are never backed up). Taken before every update, on demand, or imported.
ActivityOne audit record: who did what, on which site, when.
ExpressionA string with {{ … }} blocks, resolved by the agent on the site.
Agent portagentPort (default 7080). The mesh at /_opm/peer/ and a fallback agent GUI at /_opm/.
GUI alias portagentGuiAliasPort (default 8080). Only the agent GUI, served by the agent itself (not by Caddy), so it works when 80/443 cannot be bound.
EdgeThe router inside the agent: embedded Caddy on 80/443. Hosts (each with a TLS mode), routes (proxy or redirect, first match wins), /_opm/ reserved for the agent GUI.
RouteOne edge rule, chosen like an nginx location (exact, prefix, prefix with stop regex, regex): proxy to a container port (keep, strip or rewrite the path; request and response headers; streaming, body limit, timeouts, WebSocket), a redirect (301/302/303/307/308, with variables) or an internal rewrite.
Browser tunnelA browser tab on /_opm/app/internet that makes the cloud calls for an agent without internet.
Not-found pageAn HTML page the edge serves with 404 when no route matches, and with 503 when the proxy target is not ready.
