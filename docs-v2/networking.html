Network

Networking and ports

Each agent has an edge: an embedded Caddy server inside the agent process. The edge owns host ports 80 and 443 and routes user traffic to the containers of the site like nginx (exact / prefix / regex locations, rewrites, redirects, request and response headers, SSE, uploads, WebSockets, many hostnames, automatic TLS). An existing nginx.conf can be imported. Containers do not publish 80/443. The agent also listens on agentPort (default 7080) for the other sites, and on agentGuiAliasPort (default 8080) for the agent GUI only. Each site makes one kind of outbound connection: HTTPS to api.opm.example. A site with no internet can use a peer, or a browser tab.

Host ports: only for non-HTTP

Use Container.port[].hostPort only for traffic that is not HTTP (for example postgres 5432 for the other site). HTTP goes through the edge. A container that publishes 80 or 443, or an edge port, is a validation error.

One outbound domain

The agent connects only to api.opm.example (and to the ACME server when a host uses TLS mode acme). Image layers, file blobs and transfers come through 302 redirects to short signed URLs. The agent never connects to a Docker registry.

Port 80 is always up

The edge runs from the first start, right after the install. You do not have to wait for the first update.

  • No configuration yet (no head, or this site is not in the head): the agent runs a built-in default edge on port 80 (agent.json edgeHttpPort, null = off). Host *, no TLS. http://<ip>/ redirects to /_opm/app, /_opm/ is the GUI, and every other path shows "No configuration applied yet — open /_opm/ to approve the first update".
  • A head with no routes: /_opm/ is still the GUI; other paths show the site's not-found page.
  • 443 is bound only when a host of the edge uses TLS (internal, acme or files). The default edge never binds 443.
  • Updates never close port 80. The agent opens each edge port once and gives Caddy a copy of that socket. Every config change (default edge → first update, every update) is a graceful swap on the same socket: no refused connection, open requests get 30 s to finish.
  • Firewall. Open TCP 80 (and 443 when you use TLS, 8080 and 7080) in the server firewall (ufw / firewalld) AND in any cloud firewall in front of the server (DigitalOcean Cloud Firewall, AWS security group). The install script prints the exact ufw / firewalld commands and tests each URL from the server; a cloud firewall cannot be seen from inside the server.

Edge routing

The order of checks for every request on the edge ports.

The edge chooses a route the same way nginx chooses a location. If you know nginx, you know the edge. You can import an existing nginx.conf (below).

  1. Host. The edge picks the entry of edge.hosts for the request host: exact name first, then a wildcard (*.acme.com, one label), then "*" (any host). No entry → 404 on HTTP. On HTTPS the TLS handshake fails (no certificate).
  2. HTTP → HTTPS. If redirectHttpToHttps is on for that host, an HTTP request gets 308 to the same URL on HTTPS. Routes are not checked.
  3. Reserved. /_opm/ is the agent GUI and API on every host. An unknown /_opm/ path gets the AGENT 404 page.
  4. Route. The edge looks only at the routes for this host and this method. Then it chooses one route (next section).
  5. No route → the site not-found page with 404. Proxy target not ready (health check) → the same page with 503.

How a route is chosen

A route has a match kind and a path. The kinds are the nginx location kinds.

Regex, any caselocation ~* \.png$the same, written (?i)\.png$/img/a.PnG

The edge chooses in this order:

  1. An exact route with the same path wins.
  2. The edge finds the longest prefix that matches. Route order does not matter for prefixes.
  3. If that longest prefix has stop regex (^~), it wins.
  4. Else the regex routes are tried in their order. The first regex that matches wins.
  5. Else the longest prefix wins.
  6. Else: 404 not-found page.
  • Trailing slash. nginx sends /x to /x/ when only a route /x/ exists. The edge does the same: 301 to /x/ (the query is kept). This applies to proxy routes.
  • Order. Only regex routes have an order. The routes table shows the effective order: exact, stop-regex prefixes, regexes, prefixes (longest first). Hover the group badge to see why. Only regex rows have ↑ ↓.
  • Path. The edge matches the decoded path (%20 is a space), without the query.
  • Regex. Write regexes that Go (the agent) and JavaScript (the GUIs) read the same way. Lookahead, back-references and inline flags (except a leading (?i)) are refused with V_EDGE_REGEX.
  • Methods. A route with methods POST is invisible for a GET. Then another route can answer.

Redirects and variables

A redirect route sends the browser to a new URL. Status 301 or 308 = permanent, 302, 303 or 307 = temporary. 307 and 308 keep the method and the body. New redirect routes use 301 (nginx return 301).

Use variables in the target. The same variables work in rewrite replacements and in header values.

Keep path (prefix routes only): the rest of the path after the prefix and the query are added to the target. Route /old/ → 308 https://new.example/ with keep path: /old/a/b?c=1 → https://new.example/a/b?c=1.

Request headers and response headers

There are two groups. Do not mix them up.

GroupGoes tonginxUse for
Request headers → container (proxy routes)the containerproxy_set_headerinformation for the app: X-Script-Name, X-Forwarded-Prefix
Response headers → browser (hosts and routes)the browseradd_header, proxy_hide_headercaching, security headers, CORS
  • Request defaults. The edge keeps the client Host. It sets X-Real-IP, X-Forwarded-For (the client IP), X-Forwarded-Proto and X-Forwarded-Host. Your rows override them. Remove deletes a header.
  • Connection, Upgrade and other hop-by-hop headers are ignored (warning V_EDGE_HOP). The edge handles WebSockets and keep-alive by itself.
  • Response rows: Set replaces the container's value. Add appends a value. Remove hides the container's header. Always also adds it on errors (nginx always). Without always, a header is added only on 200, 201, 204, 206, 301, 302, 303, 304, 307 and 308.
  • Inheritance (like nginx). A host has a list. A route uses the host list, or its own list. An own list REPLACES the host list. It does not add to it. So the GUI starts an own list as a copy of the host list.
The S3 cache header: done wrong, done right

Goal: files from the small S3-like store are cached for one hour. The host adds no-cache headers to every other page.

Wrong: Cache-Control: public, max-age=3600, must-revalidate under Request headers → container. The container gets the header. The browser does not. The page is still not cached. The editor shows warning W_RESPONSE_HEADER_AS_REQUEST with a Move to response headers button.

Right: route /x/ez-terminal/s3/ → Response headers → browser → Own list: Set Cache-Control = public, max-age=3600, must-revalidate; Remove Pragma, Expires. This is the nginx

proxy_hide_header Cache-Control;
proxy_hide_header Pragma;
proxy_hide_header Expires;
add_header Cache-Control "public, max-age=3600, must-revalidate";

The own list replaces the host's no-cache headers for this route only. Test a URL shows the header under "Response headers to the browser".

SSE, uploads and timeouts

  • SSE (server-sent events). Turn Response buffering off (preset "SSE"). Every write goes to the browser at once. text/event-stream is always sent at once.
  • Uploads. Turn Request buffering off (preset "Uploads"). The body streams to the container. With buffering on, the edge keeps at most 8 MiB in memory and streams the rest. The edge never writes temp files.
  • Body size limit. Set it on the edge (Max request body; empty = unlimited) and override it per route (inherit / unlimited / size). A body over the limit gets 413 before the container sees it. nginx: client_max_body_size.
  • Timeouts. Connect = time to open the connection (1–3600 s). Read = time to the response header, and the longest pause between two pieces of data from the container (1–86400 s). Send = the longest pause while the edge writes to the container. A stream that keeps sending is never cut. A stream that is silent for longer than Read is closed. Default 60 s each, like nginx.
  • Range requests (206 Partial Content) pass through, for example for video from the S3-like store.

WebSockets

New proxy routes allow WebSockets. Turn the switch off to refuse them: an upgrade request then gets 400. You do not need Upgrade or Connection headers. A WebSocket that is silent in both directions for longer than the Read timeout is closed, as in nginx.

TLS with your own certificate on 80 and 443

A host in TLS mode files answers HTTPS on httpsPort with your certificate and plain HTTP on httpPort. Leave Redirect HTTP→HTTPS off to keep both, as with nginx listen 80; + listen 443 ssl; in one server. Upload the certificate chain as a deployment file and the key as a secret.

Test a URL

Every edge page has a Test a URL box. It runs the same resolver as the agent. It shows: the status, the route, the effective order with the winner, every rewrite step, regex groups, the redirect target or the container URL and path, the request headers sent to the container (default or route), the response headers sent to the browser (from the route or the host), timeouts, buffering, the body limit and WebSocket. Enter a body size to see a 413. Tick "WebSocket upgrade" to see a 400 on a route that refuses it. The route page has a smaller Try a path box for the route you edit.

Multiple hostnames

One site can answer many names, for example plant.acme.com (public, ACME), 10.0.1.10 (LAN, internal CA) and "*" (anything else, HTTP only). A route can apply to all hosts or to some hosts. Each name needs a DNS record (or a hosts-file entry) that points to the site host. OPM does not manage DNS.

Replacing nginx

The edge replaces an nginx reverse proxy in front of your containers. Move an existing nginx.conf like this:

  1. Open the site Edge page (cloud or agent GUI). Click Import from nginx.conf….
  2. Paste the file or upload it. Click Analyze.
  3. Read the mapping table. Every directive has a status: ok (mapped), note (mapped, read the difference), default (OPM does it by itself), ignored (no meaning for OPM), unsupported (do it by hand), error (needs your input).
  4. proxy_pass http://ez-terminal:8080 becomes a route to the container named ez-terminal, port 8080. Name your containers like the upstreams, or pick the container on the route page later.
  5. Bind each ssl_certificate to a deployment file and each ssl_certificate_key to a secret.
  6. Choose Replace (the whole edge) or Append (add hosts and routes). Check the result and its warnings. Click Apply.
  7. Save the template or draft (cloud), or create a local proposal (agent GUI). Test the URLs you know with Test a URL.

The importer follows the nginx inheritance rules. A proxy_set_header or add_header list in a location REPLACES the server list, as in nginx. nginx defaults become explicit (body limit 1 MiB when the file sets none, buffering on, 60 s timeouts). add_header always becomes a response header, never a request header.

Browser internet tunnel

A site can have no internet, and no peer with internet. Then a person opens /_opm/app/internet in a browser that has internet. The tab carries the cloud calls of the agent. The route order for each cloud call is:

  1. own internet → 2. a peer with internet (relay) → 3. the browser tunnel.
The tab polls the agent for requests, makes each request to the cloud, and posts the result back with the same reqId.

Rules

  1. Only ONE active tab (lease) per site. POST /_opm/api/tunnel/start while another lease is active → 409 conflict with the actor and start time of that lease.
  2. To move to a new tab: click "Revoke the other tab" (confirm), then Start.
  3. GET /_opm/api/tunnel/next waits ≤ 25 s and returns ≤ 4 requests. No poll for 30 s → the lease expires.
  4. Bodies over 4 MB: chunk upload, then complete with sha256.
  5. The cloud allows CORS from any origin on /v1/agent/* and on the Storage bucket. The agent signature is the authorization, not the browser.
  6. Activities: internet.tunnel.started · stopped · revoked · expired.
Security note

Every payload passes through the browser, also secrets (for example a proposal with secret values). The tab is same-origin with the agent GUI, and the actor popup is required. The agent still logs secret.fetched for each secret read. End-to-end encryption between agent and cloud is a later step.

Not-found pages

  • Create on /app/not-found-pages: a label and one self-contained HTML document (≤ 256 KB; put CSS, scripts and images inline).
  • There is no edit. To change a page, open it and use "Create a copy", then point the sites to the new page.
  • Preview on /app/not-found-pages/{notFoundPageId} in a sandboxed iframe.
  • A site uses it through config.notFoundPageId. The edge serves it for every request with no matching route (404) and when a proxy target is not ready (503). Never for /_opm/ paths. The page content travels with the proposal, so the agent has it offline.
  • Delete is possible only if no template or deployment uses it.

Distribution and relay for sites without internet

  • A site that cannot reach api.opm.example sends its signed cloud requests to a peer that can, with POST /v1/agent/relay through the mesh.
  • The peer forwards the request unchanged. The cloud checks the signature of the original site, so the relay cannot change it.
  • Reports (heartbeat, activities, staging status) of a site without internet go through the relay, unchanged. The relay peer is the first online site in slug order that has internet. agents/{siteSlug}.relayVia shows it.
  • Every site with internet polls, downloads and reports on its own. The relay is only for sites without internet.
  • Downloads (image layers, file blobs) use smart distribution, not the relay. A site gets a missing blob from a peer first. If no peer has it, ONE internet site fetches it from the cloud (the fetcher, chosen by rendezvous hashing over the blob sha256 and the site slug). The other sites copy it from the fetcher. So each blob crosses the internet once. See Smart distribution.
  • Cloud view: the sites exchange their cloud view every 10 s. The view with the newest fetchedAt wins.
  • Install on such a site: run the install command from the GUI of a site that already runs (http://<site>:7080/_opm/install/<siteSlug>).

Outbound HTTPS through a client proxy

HTTP proxy

Set "proxy": "http://proxy.client.local:3128" in /etc/opm/agent.json, or the environment HTTPS_PROXY / NO_PROXY of the systemd unit. Proxy authentication: http://user:pass@host:port.

TLS inspection

If the proxy re-signs TLS, put the client CA in /etc/opm/extra-ca.pem. Request signatures (§ auth) do not depend on TLS, so the cloud still detects any change of a request.

Long-poll

The poll keeps one request open for up to 55 s. Some proxies close idle requests after 30 s. The agent then polls again at once; no data is lost, but ask the client to allow 60 s idle time for api.opm.example.
