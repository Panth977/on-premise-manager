The cloud view carries branch (the deployment head commit); agents fetch it with GET /v1/agent/commits/{id}, stage it, and push their own commits with POST /v1/agent/branch/commits (store-and-forward). Heartbeats report the site branch and uncommitted drift. See branches-commits.md.

This page tells how the agent records what happens, how the records go to the cloud, how the status is measured, and how files move between the cloud and a site.

The activity record

Each site keeps one activity log. The log is append-only. Each record holds the hash of the record before it. Thus a change to an old record breaks the chain, and the cloud sees it.

interface Activity {
  activityId: string;        // "<siteSlug>:<seq>"  e.g. "app:1042"
  deploymentId: Id; siteSlug: Slug; seq: number; ts: Ts;
  actor: string | null;      // email, uid, or null = system
  origin: 'agent' | 'cloud' | 'system';
  type: string;              // see the catalog below
  summary: string; data: object;
  prevHash: Sha256 | null;   // null only for seq 1
  hash: Sha256;              // sha256(prevHash + canonical JSON without hash fields)
  uploadedVia: 'pipe' | 'manual' | null; uploadedAt: Ts | null;
}
Each record holds the hash of the record before it. The activityId is the site slug plus the sequence number, so the same record always has the same ID.

The upload pipe

The upload pipe is a separate component of the agent. It has one job: send the records that the cloud did not acknowledge yet.

  • It sends all records after the last acknowledged seq, in batches of 500, to POST /v1/agent/activities.
  • The API upserts by activityId. It never changes a record that exists. It answers { ackSeq }: the highest stored seq.
  • If the site has no internet, a peer site with internet relays the signed request (POST /v1/agent/relay).
  • If no path to the cloud exists, the pipe waits. It does not lose records.

  1. DownloadIn the agent GUI, open /_opm/app/{siteSlug}/activities/download (* = all sites). The agent makes an .opmlog file.
  2. SendThe site operator sends the file to the operations team, for example by email or USB.

Activities and the root audit log

Changes inside a deployment write activities to that deployment's log. Saving a draft section or a site writes draft.updated with the list of changed paths but never the values. Starting a transfer writes transfer.sent with stage started, and finishing the upload writes it again with stage uploaded. Deleting a transfer writes transfer.deleted. Uploading a .opmlog file by hand writes activities.uploaded with the counts, and deleting a deployment writes deployment.deleted. Everything outside a deployment (catalog, templates, tags, accounts, and creating, changing or deleting a deployment) goes to the root audit log, success or failure, with a before → after diff and secrets shown as ***.

Debug log

The debug log is the agent's own log. It is not an activity log. It helps when the agent does not do what you expect.

  • Format: JSON lines. Each line: { "level": "debug|info|warn|error", "ts": Ts, "module": string, "msg": string, "fields": object }.
  • Modules: cloudlink, mesh, stager, expr, driver, port80, tunnel, health, coordinator, snapshot, pipe, transfer, auth, gui.
  • Rotation: one file per day. Keep 7 days or 200 MB, whichever comes first.
  • View: /_opm/app/{siteSlug}/debug. * merges all sites, sorted by time.
  • Download: include it in an .opmlog bundle (activity type debug.downloaded).

Status and uptime

In the cloud

  • Each agent sends a heartbeat every 30 s (POST /v1/agent/heartbeat, or the poll).
  • A site is online if its last heartbeat is less than 90 s old.
  • The cloud keeps one document per site per day (uptime/{siteSlug}_{yyyymmdd}) with 24 hourly online fractions.
  • Page: /app/deployments/{id}/status with a 30-day heatmap.

On the site

  • The agent samples each site and each container every 30 s.
  • It keeps the raw samples for 24 h, and hourly buckets for 30 days.
  • A container sample is "up" when the container is running and its health check passes.
  • Page: /_opm/app/{siteSlug}/status (* = all sites).

Green = up. Red = down. Grey = no data (the site was not reachable; the agent fills its own gaps when it is back, the cloud cannot).

Transfers: send and receive

Both GUIs have ONE Transfers page per site with two columns: on the agent (/_opm/app/<site>/transfers, Agent › Transfers) left = Send (this site → cloud), right = Receive (cloud → this site); in the cloud (…/sites/<site>/transfers) left = Send (cloud → site, browser upload only), right = Receive (from the site). The old send / receive URLs redirect (SPEC §21 #100).

Store-and-forward, both ways

Nobody has to be on the other end. Site → cloud: the agent stores the file on the site first and answers at once (queued); its transfers loop creates the cloud transfer and uploads the missing 8 MiB parts whenever the site has a route to the cloud (direct or relay through another site; never the browser tunnel, whose request bodies are ≤ 4 MiB), retrying with backoff 15 s → 5 min (uploading → stored). The cloud keeps it whether or not anyone has the deployment open. Cloud → site: the cloud stores the browser upload; the agent fetches it the next time it is online (pending → downloading → on this site) and reports fetched, so the cloud shows "on the site" (fetchedAt). Nobody needs the agent GUI open.

Send › Path opens a picker over the whole server filesystem (from /, one level at a time: GET /_opm/api/sites/<site>/transfers/fs?path=&hidden=, session only, not logged). The agent is a host binary (root on a standard install), so it reads the host's real files; entries it cannot read show "no permission". Files only — make a .tar.gz of a folder on the server first. Safety policy (sending refused, also through a symlink): the agent's own home (site key, database, secrets), its agent.json and install token; /proc, /sys, /dev, /run; /etc/shadow, /etc/gshadow (and - backups), /etc/sudoers, /etc/security/opasswd; SSH host private keys; anything that is not a regular file. Every send is the activity transfer.sent with source (browser | path) and sourcePath.

interface Transfer {
  transferId: Id; deploymentId: Id; siteSlug: Slug;
  direction: 'to-site' | 'to-cloud';
  fileName: string; sizeBytes: number; sha256: Sha256;
  storagePath: string;       // transfers/<deploymentId>/<transferId>
  createdAt: Ts; createdBy: string; note: string;
  expiresAt: Ts;             // createdAt + 30 days
  status: 'uploading' | 'ready' | 'saved-on-server' | 'downloaded' | 'expired';
  savedPath: string | null;
  fetchedAt?: Ts | null;     // cloud, to-site: stored on the site (agents ≥ 0.11.2 report it)
  sourcePath?: string | null; // agent, to-cloud: sent from this server path
  delivery?: { phase: 'queued' | 'uploading' | 'stored' | 'pending' | 'downloading' | 'on-site';
               bytesDone: number; attempts: number; lastError: string | null; … }; // agent API only
}
