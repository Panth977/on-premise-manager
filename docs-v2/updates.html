Change flow

Config, proposals & updates

Agent 0.14.1: one action — Commit (SPEC §21 #105)

There is no working copy and no draft any more. Every edit stays in your browser (kept in local storage, so a reload loses nothing) until you press Commit… and give a message — that writes the commit directly. The bar on every config page shows N changes (not committed) · Discard · Review · Commit…; drawers and dialogs Apply into it, there is no Save button. If someone else committed meanwhile, your changes are rebased onto the new head (automatically when nothing conflicts). On a site, a Commit in the agent GUI also applies the changes to the containers (a failed apply writes no commit); there, "uncommitted" means only changes made on the server outside the agent — commit those first. Details: branches-commits.md §15.

Agent 0.14: branches replace proposals (SPEC §21 #104)

Templates, deployments and every site are now branches of commits. Edits go into a working copy; Commit… (a message is required) makes a commit. The newest deployment commit is what the sites should run — there is no proposal and no approve countdown any more. In the agent GUI Branch page a person on the site merges the cloud commit (all of it, or cherry-picked items; deletions show as "remove locally"); the apply engine below (snapshot, start order, readiness, rollback) still runs it. Changes made on the server by hand show as uncommitted and must be committed or discarded first. Agents older than 0.14 still get the commit as a proposal. Full design: branches-commits.md. The rest of this page describes the apply engine and the pre-0.14 proposal flow.

The config is one document for the whole deployment. Every change makes a new revision. A revision waits as a proposal in the agent GUI. A person approves it once, for all sites. The agent takes a snapshot first. If any step fails, every site rolls back.

Template changes never flow by themselves

A deployment made from a template is a copy. Editing the template (variables, files, sites, containers) or deleting it never changes the deployment, and nothing updates in the background. To bring template changes in, open Template sync in the deployment: it compares the template when you last synced (the base), the template now, and your draft. You tick the template changes you want, choose for every conflict (take template, keep mine, or a merged value), preview the validation and click Apply to draft. That only edits the cloud draft. You still review the Diff and publish a proposal, and a person still approves it on a site, like any other change. Changes you did not take stay listed as “skipped” until the template changes them again.

The revision chain

RuleWhat happens
Linear on the sitesEvery agent stores the same head. A new revision is always a child of the head.
Cloud publishDiff page → "Publish proposal" → revision { parentRevId: deployment.head.revId, origin: "cloud", config: draft } + proposal status published. Agents get it on the next poll.
StaleThe sites' head is no longer the parent (a local change happened). The agents mark the proposal stale. The cloud shows "rebase needed".
RebaseDiff page → "Copy head into draft" → edit again → publish again. Nothing merges silently.
SupersededA newer cloud proposal marks older proposals that are not approved as superseded.
Local proposalAn edit in the agent GUI makes a revision with origin: "agent" and actor: email. It uses the same gate and apply steps.

Staging on every site

Staging is automatic and needs no approval. It runs on every site of the current and of the proposed config. Each site reports its staging state to the proposal.

Where the blobs come from (steps 2 and 4)

Each site gets a missing image layer or file blob from a peer first (local network). If no peer has it, one internet site (the fetcher, by rendezvous hash) downloads it from the cloud, and the others copy it from that site. Every copy passes a sha256 check. The staging table shows the source per blob: cloud or peer <slug>. Each site with internet polls the cloud on its own; a site without internet gets the newest cloud view from its peers (latest fetch wins). See Smart distribution. Gate condition (b) does not change: every site must still be reachable.

The gate: when the Approve button shows

The Approve button is visible only when all four conditions are true. Tick them to see the button.

Approve, then apply

Approve → a 60-second countdown (you can cancel; hold ⏩ Hold to fast-forward to run it ×2, then ×4 — never shorter than 15 s, the agent counts it; a fast-forwarded approval is recorded as "fast-forwarded (×4, 18 s real)") → a dialog asks you to type ACCEPT. The dialog shows the declared actor (the email from the "Who is working right now?" popup); that email is written as approvedBy. The agent where you approved becomes the coordinator.

Volume starter content

Staging also fetches the starter content of site volumes (files and archives, like file blobs) and checks it. It fails when a volume changed between folder and single file while it holds data ("use a new volume name"). During APPLY the agent writes starter content into new or empty volumes, before the containers start. It never writes into a volume that has data. The review shows "seed changed — applies only to new / empty volumes" when you change the starter content of an existing volume. See Starter content.

Apply order

Sites start in depends order. Inside a site, containers start in depends order. A cycle is a validation error, so staging fails. Change the dependencies below.

Automatic rollback

If any step from snapshot to verify fails, every site restores the pre-update snapshot. Pick where the update fails.

    Why did it fail? Container logs

    • Before the rollback touches a container that failed APPLY or VERIFY, the agent saves: the last 200 log lines (secrets hidden), the exit code, "OOM killed", the restart count, the port map, and every health check (time, pass / fail, inside the start period or counted, message).
    • Agent GUI → Updates: the result of a failed update has a Failed containers section. Open a container to see its error, health history and log lines.
    • Cloud → Activities: the update.failed activity carries the same summary and the last 40 log lines; its drawer shows them under "Failed containers".
    • On the server: the failed container is stopped and kept as <name>-failed-<unix time>, so docker logs <that name> works. It is removed after the next successful update or after 24 h.
    • Running containers: Agent GUI → a site → Status → Container logs: tail 200 / 1000 / 5000, search, follow, Download.
    • A container that keeps crashing shows "container is restarting: last exit code N, M restarts". Look at its log lines for the reason (for example a missing variable or a database it cannot reach).

    Proposal states

    StatusMeaning
    publishedCreated in the cloud (or locally). Agents know it.
    stagingAt least one site downloads or validates.
    readyEvery site is staged. The gate can open.
    approvedA person typed ACCEPT. approvedBy (the declared actor email) and approvedAt are set.
    applyingLock, snapshot, apply, verify run.
    appliedHead = this revision on every site.
    failed-rolled-backA step failed. Every site restored the snapshot. result.message tells why.
    staleThe head is no longer the parent. Rebase in the cloud.
    supersededA newer cloud proposal replaced it before approval.
